# Agent Note: 按「回答什么问题」划分存储位置，取消 docs/plans/

Status: implemented

## Problem

[导入 pzd_Workflow 通用规则](2026-10-28-adopt-pzd-workflow.md)之后，PZD 有七处地方可以写文档：`docs/architecture.md`、`.agents/notes/`、`docs/plans/`、`docs/work/`、`.ai/知识库/`、`.ai/记忆.md` 与 `.ai/交接/`，以及规则文件。但各自存什么没有划清，有三处会打架：

- **ADR 有两份**：`architecture.md` §19 的表格写了每个决定的理由，`.agents/notes/` 也是记「为什么选 X」的地方。
- **计划和 `proposed` 笔记重叠**：通用规则要求复杂改动先在 `docs/plans/` 落盘计划，计划里要写决策、备选、风险；`proposed` 笔记写的也是「还没做的方案 + 备选」。同一个方案会写两遍。
- **两套状态表示**：笔记用文件夹表示状态，票用文件头 `状态：`，没有规定谁用哪种。

步骤 1–2 的教训是，同一个结论写在多个地方，最终一定会互相矛盾。不划清边界，这次还会重演。

## Decision

`.ai/规则/存储映射.md` 是 PZD 存储位置的唯一正文，要点如下：

- **按「这份文件回答什么问题」决定位置，一个问题只有一个家**：
  - 现行结论写 `architecture.md`
  - 为什么写决策笔记
  - 做什么、做到哪写票
  - 跨项目教训写知识库
- **`architecture.md` 只写结论，不写理由**。§19 不一次性迁移：某条决定第一次被重访时，才为它写一篇 `implemented/architecture/` 笔记，并在同一个提交里把该行的「理由」改成指向笔记的链接。新决定只在 §19 加一行结论和链接。
- **PZD 不建 `docs/plans/`**。计划里的决策、备选、风险写成 `proposed` 笔记；目标、范围、责任文件、接口、步骤、验证、恢复方式写在票里。通用规则里默认用到 `docs/plans/` 的四处，`存储映射.md` §4 逐条写明了在 PZD 里的替代做法。
- **两套状态表示分工**：笔记用文件夹表示状态，状态变化就是 `git mv`；票用文件头表示状态，因为票的状态变化频繁。不混用。
- **决策笔记不建索引**，沿用目录加 `rg` 的检索方式；知识库的索引只列主题文件和一句话范围，不复述条目内容。
- 派生物和过程记录（看板、审计过程、验证日志原文）不入库。

## Alternatives considered

- **保留 `docs/plans/`，照 pzd_Workflow 的默认做** — 最强理由：通用规则的开发流程、任务映射、任务发现都默认会看 `docs/plans/`，保留就不用在 PZD 里写四条替代规则，以后同步上游也少一处差异。没选，是因为计划里「决策、备选、风险」和 `proposed` 笔记是同一件事，两边都写就是重复正文；剩下的「步骤、验证」本来就是票的内容。用四条替代规则换掉一类重复，划算。
- **把 §19 的 ADR 一次性迁移成笔记** — 最强理由：一步到位，从此 `architecture.md` 里不再有任何理由，规则立刻完全成立。没选，是因为 §19 有 17 条决定，现在没有任何一条在被重访；一次性写 17 篇笔记，等于凭空补写理由和备选，违反「备选只写真考虑过的」这条规则。
- **给笔记也建一个 `INDEX.md`** — 最强理由：人浏览时一眼就能看到所有决定，不用翻目录。没选，是因为索引就是第二份正文，每次新增、改名、归档都要同步，迟早和实际文件对不上；路径已经编码了状态和类别，`rg` 加目录切片足够检索。

## Consequences

- **收益**：
  - 每类内容只有一个位置，新建文件前查一张表就知道写哪里。
  - 方案不会同时存在于计划和笔记两处。
  - `architecture.md` 会逐步变成纯结论文档，理由集中在笔记里。
- **代价**：
  - PZD 和通用规则多了一处差异（不用 `docs/plans/`），依赖 `存储映射.md` §4 的四条替代规则。以后同步上游时，如果上游又新增了对 `docs/plans/` 的依赖，需要补充替代规则。
  - §19 在相当长一段时间里是「部分理由在表里、部分在笔记里」的混合状态。
  - 不建索引，人想浏览全部决定时只能看目录。
- **重访信号**（出现任一情况就重新评估）：
  - 有票或笔记里出现了本该写在另一处的内容，比如笔记里记了票的进度、票里写了完整的备选论证。
  - 上游 pzd_Workflow 新增了对 `docs/plans/` 的依赖。
  - 维护者需要一个能浏览全部决定的总览。
