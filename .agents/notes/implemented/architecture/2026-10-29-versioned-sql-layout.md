# Agent Note: 版本化 SQL 的放置与命名

Status: implemented

## Problem

`architecture.md` §2 把 `db/master`、`db/tenant` 定为版本化 SQL 的家，§15.4 又要求「先迁移后部署」，但仓库里既没有目录也没有命名约定。没有约定时最贵的错是两种：一是序号被复用或按时间排序，导致不同环境执行顺序不同；二是有人把 `CREATE DATABASE`、账号授权、凭据写进迁移文件，让迁移脚本变成运维脚本。这两类错都只有在生产上才暴露。

## Decision

- **两库两目录**：平台级对象（租户、套餐、菜单与权限码、Quartz 表）在 `db/master/`；业务表在 `db/tenant/`。业务表不带 `tenant_id`，隔离靠「一个租户一个库」。
- **命名 `NNNN_简述.sql`**：4 位十进制序号 + 下划线 + 小写英文简述，序号**全局递增、永不复用**，执行顺序只看序号。一个文件一次逻辑变更。
- **只前滚**：不写 down 脚本，出错用新脚本修正；破坏性变更走 expand-contract 两段。
- **迁移文件不承担运维职责**：不写 `CREATE DATABASE` / `USE` / 账号授权 / 凭据 / 真实主机名。
- **顺序固定**：先迁移、后部署代码；租户侧灰度 → 全量，单租户失败不阻塞其他租户并单独标记重试。
- **执行器留空**：DbUp 或自研由维护者拍板（consensus §4 待决 2）。本约定只约束放置、命名、顺序，换执行器不影响这些规则。

## Alternatives considered

- **时间戳命名（`20261029_1200_xxx.sql`）** — 最强理由：多人并行时不撞号，合并顺序天然可复现。没选，是因为两个人在同一分钟建迁移的概率不为零，而序号冲突在 review 里一眼看得出；时间戳也会让「第几次变更」这件业务事实变难读。
- **Flyway 风格 `V1__xxx.sql` 前缀** — 最强理由：业界最熟，工具直连。没选，是因为它把「版本号」和「迁移序号」混成一个概念，而 §15.1 的版本号属于产品发布，不该被数据库迁移复用。
- **按 feature 分目录（`db/master/tenant-core/`）** — 最强理由：一张票的 SQL 聚在一起，review 时边界清楚。没选，是因为执行顺序必须全局唯一，按目录切完还得再维护一份跨目录序号表，等于多一层容易失同步的映射。

## Consequences

- **收益**：执行顺序在任何环境里唯一且可复现；迁移文件与运维动作分离，凭据不可能被提交进来；序号一眼看出变更次数，review 时能对着票号查。
- **代价**：并行开发时两人可能同时占用下一个序号，需要 rebase 时改号；序号一旦占用不能回收，编号会随废弃迁移留下空洞。
- **重访信号**：执行器选定后若它自身强制另一套命名（例如 Flyway 的 `V` 前缀）；或者并行票数量增加到序号冲突成为常态；或者引入多 schema / 分库分表让「一租户一库」不再成立。

## Verification

```bash
ls db/master db/tenant          # 两个目录都在，README 写清命名与顺序
git grep -nE 'CREATE DATABASE|USE |IDENTIFIED BY' -- db/   # 期望无命中
```

迁移文件出现后，检查顺序：`ls db/tenant/*.sql | sort` 与序号排列一致。
