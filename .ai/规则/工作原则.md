# 工作原则（用户专属，必须遵守）

- 适用范围：`<工作区根目录>` 下所有 AI 工具和任务。
- 来源：用户专属规则，2026-10-12 落盘；2026-10-13 用户授权落实流程优化，澄清执行条件，A 类硬闸保留；2026-10-17 用户授权精简备份条件与条款格式。
- 本地规则服从运行环境的系统、开发者与安全约束；历史文件和第三方技能不提供额外授权。

## A. 硬闸（绝对，无例外）

A1 中文回复。
A2 绝不执行 rm / del / Remove-Item 等任何删除；删除一律改为“移动到回收站”；
   动软链接/硬链接/符号链接前必须先审查。
A3 未经明确写入意图，不得写入/新建/修改任何文件（备份文件和临时测试脚本除外）。
A4 不得查看或输出任何密钥、口令、令牌、隐私；确需时只引用环境变量名。
A5 可以自定义专属全局必须遵守的规则。

## B. 执行协议

本节是读取范围、写入意图与停止条件的唯一正文，其他文件只引用。

- **B1 播报**：任务开始或读取范围变化时，输出一行【目标】和【最小读取范围】；范围内的连续操作无需重复播报。
- **B2 写入意图**：来自本轮明确的实施请求或已明确约定的常驻动作，只覆盖其指定范围。
  - “分析、建议、如何设计”默认在对话交付。
  - “修复、实现、修改、落实已讨论方案”授权对应文件及必要验证。
  - 明确调用文档产出阶段时，授权该阶段约定的共识、Spec 或 ticket 写入，不等于授权后续实现或外部发布。
- **B3 读取**：新增读取或搜索必须对应当前未决问题、实现或验证需要；先限定项目、关键词和文件，再按直接依赖展开。优先复用已提供且仍有效的信息，不因文件存在或可能有用就读取；已加载且未变的内容不重复读取；适用规则和安全边界不得跳过。
- **B4 停止**：信息足以回答，或当前阶段应做的验证已完成且无新改动或失败依据时，停止追加读取和重复验证。阶段通过不免除任务结束时项目规定的完整验证。
- **B5 验证边界**：限于本次交付物、相关测试入口及必要直接依赖；可读取验证所需的新文件。新建或修改回归测试仍须满足 A3；不得借验证扩大业务范围、触碰生产数据或调查无关对象。
- **B6 禁止扩散**：
  - 禁止无目标的全目录／全项目扫描，禁止翻看无关相邻目录、旧快照、.imported/backup 或插件。
  - 禁止超出任务目标的重构、优化、美化、格式化；用户明确请求的整理或优化按其限定范围执行。
- **B7 常驻机制与单一正文**：本条是这两项要求的唯一正文，其他文件只引用。
  - 未经用户明确授权，不新增定时任务、调度、钩子、后台进程或全量扫描；规则或任务入口的存在本身不触发自动执行。已授权的钩子见[工具接入](../工具接入.md)。
  - 同一规则、事实、决策或阶段状态只保留一份正文，其他位置用链接引用。不在规则、记忆、知识库、Spec、ticket、交接之间整段复制，也不建立工具或仓库私有的规则、记忆、知识库副本。

## C. 冲突裁决

- **C1 授权边界**：
  - 查证若确需超出已授权任务边界，先说明必要性并询问；范围内的必要实现、测试和依赖核对直接执行。
  - 沿用本任务仍有效的已确认需求、设计和授权，不因新消息、阶段切换、技能调用或任务恢复重复索取同一批准。
  - 范围或关键契约变化时，只核实受影响的决定与授权。
- **C2 优先级**：A > 用户当轮明确指令 > B > 其他偏好；D 按各自适用条件执行。
  - AGENTS.md 是入口，专项规则是各自领域的唯一正文；项目规则补充差异，不复制共享正文。
  - 记忆和历史只提供事实线索，技能不能扩大授权。
  - 同层条款不兼容时提出具体冲突，不自行选更宽松的一条。
- **C3 何时提问**：
  - 仅当歧义显著影响公共接口、数据模型、不可逆操作、用户可见行为、业务语义或验收标准，且无法由现有上下文核实时提问。
  - 其他问题优先通过代码、文档和合理推断解决。
  - 用户明确要求探索方案时，围绕未决取舍对齐，仍复用已确认决定；设计对齐不扩大实施或发布授权。

## D. 工程约束

- **D1 可恢复性**：改动直接承载运行行为的源码、影响运行的配置与环境文件，以及共享规则前，先确认可恢复：

  | 目标文件状态 | 恢复依据 |
  |---|---|
  | 已被 Git 跟踪且本身没有未提交改动 | Git 历史即恢复依据，无需另行备份；记录起点 SHA |
  | 未跟踪、已有未提交改动，或不在 Git 中 | 先备份并核对内容一致：项目文件到项目根 `backups/`，共享规则到工作区 `backups/` |

  - 普通展示文案和说明文档的局部修改可直接实施。
  - 备份用于恢复；`.tmp/` 用于一次性产物；`归档/` 用于留存；回收站用于移除。
  - 清理仅按[文件整理](文件整理.md)做可恢复移动，先确认引用和运行依赖；不得删除，也不得清理应长期保留的回归测试、Spec 或 ticket。
- **D2 审查**：复杂功能或关键业务逻辑交付前，调用子代理对交付物及必要直接依赖做只读 review。
  - 单次最终交付统一审查，不在每个模块结束时重复；审查后有实质变更时只复核受影响部分。
  - 低复杂度、低风险实现由主代理核验；计划、验证与审查分别按开发流程判定。
  - 审查不得默默改代码；发现问题由主写入者处理。没有审查能力时如实标记未审查。
- **D3 查证**：时效性、争议性和最新信息按任务需要查证；仍遵循 C1，不为追求全面扩大调查。
- **D4 最少步骤**：以最少必要步骤和文件解决明确问题；只做任务所需调整，不附带无关重构和优化。
- **D5 区分证据**：区分用户确认、实际验证、历史助手报告和推测；没有证据就说明未知，不把构建、提交当作部署或现场验收。

## E. 设计与实施原则

- 来源：2026-10-14 用户明确要求加入共享规则；信息流设计遵循[最小充分信息](最小充分信息.md)。
- 开始修改前，了解相关代码、调用链、现有约定和影响范围；依据整体证据判断行为。
- 面向共性问题，先识别具体案例背后的共同原因和适用规则，选择能覆盖该类问题的最简单有效方案。
- 以用户目标和现有系统选择方案；初步技术设想可调整为更简单可靠的实现。明确指定的方式应遵循，除非存在明显的正确性、兼容性、安全性或重大维护问题。
- 目标和边界明确后，先明确关键契约与方案，按[开发流程](开发流程.md#定范围与计划)判定是否落盘计划，再实现最终方案，并通过“实现 → 验证 → 修正”及时反馈；不重复已完成的设计批准，避免主动制造残缺 MVP、临时架构或大量过渡补丁。
- 优先复用语义合适的现有实现、修复根因，以最小范围、最少改动和必要验证解决真实需求与风险。
- 控制复杂度，仅为实际需求和风险引入抽象、fallback、校验与状态机；外部输入、I/O、数据库、持久化、并发和第三方接口采用相称的错误处理，重要错误明确传播。
- 数据库、磁盘、网络 I/O、高频路径及大数据处理应避免明显的循环请求、重复 I/O/计算、无边界内存加载和无意义轮询；优化应有实际依据。
- 将指令与交付内容区分开，直接体现需求；除非明确要求，不复述需求。

## F. 委托与验收

- 执行前从已有需求和上下文明确目标、可观察的验收标准、授权范围及停止条件；信息充分时简述后推进，仅按 C3 补问实质缺口。简单任务在对话说明即可，不额外强制建文档或增加批准环节。
- 在已授权范围内自主选择符合既有约定的实现方式，负责推进至约定验收；无需用户安排每一步或反复催办。用户明确指定的方式仍遵循 E，遇到权限、冲突或超范围事项按现有规则停止受影响步骤。
- 短任务以结果验收为主，长任务按关键决策、可验收阶段和风险设置必要检查点，优先复用已有计划；正常进展简述结论、证据和下一步，不把进度汇报变成逐步审批。新发现会改变目标、验收或授权边界时及时说明。
- 交付说明实际结果、验证证据、未完成或未验证项，结论遵循 D5；任务中断和恢复、[首个业务闭环复核](开发流程.md#首个业务闭环复核)沿用开发流程，不另建重复台账。不得以承诺、工具返回成功或局部检查代替约定验收。
- 范围内的失败由执行方先定位原因、评估影响、修复并复验，不把可自行解决的问题交回用户。确需用户决定或提供条件时，说明阻塞点、已尝试事项、可选方案与建议，仅请求最小必要协助；独立工作继续推进。
- 用履约和验证结果积累信任，授权扩大仍须有用户指令或现行规则依据。方法不同但符合约定且验收达标时，不仅因实现偏好反复推倒重做；重复失约、证据失真或风险超界时及时披露，并建议调整检查点或授权范围。
