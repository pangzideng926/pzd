# Git 与 worktree

触发：需要判断是否隔离、创建 worktree、提交、推送、集成或同步时读取。本文件是 Git 操作细则的唯一正文；开发与验证见[开发流程](开发流程.md)。

## 通用约束

- 所有 Git 命令显式使用 `git -C <实际工作目录> ...`；不在非 Git 的工作区根目录执行 Git。
- 开始修改前记录：仓库绝对路径、原分支、当前 HEAD、已暂存与未暂存改动。
- 禁止强推；禁止提交、回滚、删除或清理他人内容；不擅自 stash、checkout 或丢弃改动。

## 何时隔离

| 目标工作树状态 | 做法 |
|---|---|
| 干净 | 可在原目录开发；分支选择仍按下节判断 |
| 存在不属于本任务的未提交改动（无论新旧、归属是否明确） | 基于当前 HEAD 创建独立分支与 worktree |
| 已有本任务 worktree | 核对归属与起点后复用 |
| 纯只读探索，或修改非 Git 的共享文件 | 不建 worktree |

- 他人改动不擅自纳入、覆盖、回退或隐藏。
- 任务依赖原目录的未提交改动时，先明确如何带入；新 worktree 不自动带入，也不自动 stash、复制或丢弃。
- 隔离受权限、工具或冲突阻塞时，保留原现场，只继续独立的只读调查、基线验证和最小接手记录，条件满足后再恢复依赖步骤。

## 分支准入与合并方式

- 原目录／worktree 只决定工作目录，不决定是否可以写入目标分支。业务写入前核对已明确的目标、现行项目政策、实际权限和本次授权；不能凭工作树干净、角色名称或历史推送成功推定允许直推。
- 目标受保护、项目要求合并请求，或直接写入许可未知时，使用本任务分支，通过 PR/MR 交付。干净原目录也遵循此要求；已有本任务分支先核对再复用，不为试权限向目标推送。只有政策、权限及授权明确允许时才直接向目标交付。
- 来源或目标需要更新时先核对相关远端引用；目标变化涉及集成差异时，在任务分支整合并验证受影响内容，有冲突按停止条件处理。分支准入不绕过证据、审查、批准或其他保护策略。
- 通用规则仓本地维护与发布另按[规则同步](规则同步.md#修改与发布单独明确授权后)执行；本文件的业务固定收尾不授予规则仓提交、推送或创建 PR/MR 的权限。

## 创建 worktree 与任务映射

1. 位置：`<项目>/.worktree/<任务编号>/`，不放在项目平级或更高目录。任务编号沿用现有 ticket，否则用不冲突的“日期-短名”。
2. 创建前核对：仓库根、原目录分支／提交及改动、路径与分支占用、合入目标。不覆盖或强制复用其他任务的工作树；既有工作目录记录真实路径，不擅自搬动。
3. 创建后记录实际起点 SHA（保留为基线，不随任务提交更新），并确认共享规则入口在新 worktree 中可读。
4. 每个需要修改的 Git 仓库一行映射，不按 API/Web 等模块机械拆分；同仓多模块共用一个 worktree。

映射写入位置，按顺序取第一个可用项：已有 ticket 任务头之后 → 已有 `docs/plans/` 计划 → 简单单会话任务可只在对话 → 需跨会话且前两者都没有时，写实际工作目录的 `docs/work/<任务编号>/任务.md`。跨仓只保留一份主记录，其他资料引用；任务头按[统一状态](开发流程.md#任务状态与中断)，不为建立映射绕过隔离去改主仓。

最小映射模板（占位内容须替换为实际核对值）：

```markdown
任务：<现有编号或日期-短名>
主任务文档：<已有 ticket 或任务文件的实际路径>
| 原仓库绝对路径 | 实际工作目录（worktree） | 任务分支 | 起点分支/引用及 SHA | 合入目标分支 | 本仓修改范围 |
|---|---|---|---|---|---|
| <仓库路径> | <工作目录路径> | <实际分支> | <已选定引用>@<实际 SHA> | <已确认目标> | <模块或文件范围> |
```

- 开始或接手时对照映射核对仓库归属、分支和现有改动；不符时先定位原因，不自动切换或覆盖现场。
- 业务修改、构建、测试及 Git 命令都指向映射中的实际工作目录；新增写入仓库先补映射与对应 worktree。名称相似的副本不自动成为写入目标。
- 映射不扩大客户端文件权限。跨仓分别验证、提交、推送并记录，一个仓库完成不代表全部完成。

## 状态检查点

- 认领、中断或接手需要保存状态时，可在已有提交／推送授权内建立检查点，不受下节“完成验收和必要审查后”的收尾条件限制；不因此新增发布权限或放宽目标分支准入。未完成实现的检查点仅保存在任务分支，标明未验证或已有失败，不能当作可合并候选。
- 本机恢复只需保存任务资料及必要说明，未完成代码可以留在原工作目录；跨设备接手时，在同一任务分支保存接手必需的本任务改动并推送，记录相对资料路径、分支及提交，不能只推状态而遗漏接手依赖，也不夹带他人改动。
- 多人跨设备认领前及开始实施前，在授权范围内刷新已确认共享远端的相关任务引用，核对已发布的主写入者；认领状态须提交并推送任务分支后才可视为已共享。发现重复认领时先明确移交；未获同步授权、推送失败或无法确认最新认领时，保留本地记录并说明可见性限制，不把“本地未发现”当作可抢占依据。状态文件和推送均不提供跨机器互斥，冲突未解决前停止重叠写入。

## 收尾：已授权的固定动作

适用于本次改动所在的子仓库，在完成验收和必要审查后执行；用户另有指令或规则仓有专门发布约定时遵循其范围。非 Git 的共享根文件通过备份及改动记录交付，不初始化仓库、不伪造提交。

- 多阶段任务完成一个可独立验证的阶段后，优先创建本地提交作为检查点。
- 有版本化计划、ticket 或任务文件时，先在任务分支回填状态、验收、审查和遗留事项，再提交。尚未发生的提交／推送／合并不预填成功；当轮最终 SHA 与结果写在交付回复（及已有真实交接），任务资料可在后续实际接手时核对补齐，不能为追记结果反复制造文档提交。

1. **提交**：检查暂存区 → `git -C <目录> add <本次文件>` → 核对最终待提交 diff → 用简体中文、沿用既有格式提交。暂存区已有非本次改动且无法安全隔离时，停止并说明冲突，不撤销他人的暂存状态。
2. **推送来源分支**：核对已配置远端与目标；首次用 `git -C <目录> push -u origin <任务分支>:<同名远端任务分支>`，已有分支同样明确来源和目标。推送不等于合入。
3. **按准入方式集成**：需要 PR/MR 时按下节执行；允许直接集成时，也须有明确集成授权、目标与候选适用证据，主工作树干净且未混入其他任务修改。主线较起点有变化时先整合并验证实际结果；有冲突时停止。不能用本地合并后直推代替要求的 PR/MR。
4. **按工作模式收尾**：原目录模式按用户约定保留任务分支或切回开始前分支；未切换则跳过。worktree 模式保留任务 worktree 与任务分支，不在其中切回，不改变原目录分支。
5. **原目录同步**：仅在已有授权、分支符合预期且不影响现有改动时，以明确路径 fetch、`pull --ff-only`，记录结果；等待 PR/MR 不代表已合入，也不无条件拉取原目录。

- 任务结束不自动移除 worktree、删除分支或搬动目录；确需整理时遵循[文件整理](文件整理.md)。

### PR／MR 交付

1. 在已授权的项目交付范围内复用或创建合并请求，记录来源分支及完整 SHA、目标分支、问题与变更、验证和未覆盖项；不重复建单。创建或更新请求不等于获准批准、合并或部署。
2. 按平台要求等待必要 CI、审查及批准；来源或目标改变时重核证据适用性。不能代替其他角色批准，也不关闭门禁来放行；检查失败或证据不足保持待修复／待验证。
3. 只有合并授权、平台权限和必要条件全部满足时才通过平台合并。缺少当前可用的 API、CLI 或已获授权界面时，先完成分支和可审阅的请求标题、说明、来源与目标，再明确“PR/MR 未创建”或具体待办，按需请求最小协助；不强制安装工具。
4. 合并后按下节核对远端目标 SHA、最终内容及适用验证，再同步允许更新的本地目录。批准不等于合并，平台显示已合并也不单独证明目标行为正确。

## 停止条件

- 切换前本地剩余改动可能与目标分支冲突 → 先请求确认。
- detached HEAD、无远端或无对应分支、推送失败、权限不足 → 不猜测目标、不另配远端，停止依赖步骤并报告。
- fetch/pull 失败，或原目录无法快进 → 停止依赖步骤，不擅自 merge/rebase。
- 集成冲突 → 保留现场并报告；独立验证与文档收尾仍可完成。
- 代码完成但推送失败 → 分别记录“验收已通过”和“同步未完成”，不写成整套收尾完成。

## 状态判定

- 在已有任务记录中分别维护以下状态，不另建台账；一项通过不能代替其他项。

  | 维度 | 判定与报告 |
  |---|---|
  | 修复与验证 | 分开记录“已修改／待修复”和“未运行／失败／已验证”，关联被测候选与范围；失败、环境阻塞或证据不足保留未解决事项 |
  | PR/MR | 分别记录未创建、待审、待合并、已合并或已关闭未合并（不涉及则注明）；关联请求位置及来源候选，批准不能代替合并 |
  | 集成 | 已验证但未进入目标时写“已验证，待集成”；已合入须记录目标引用、解析 SHA、核对时间、集成方式和对应证据 |
  | 发布与运行 | 提交、任务分支推送、目标分支推送、部署、现场验收分别记录；正常推送并核对远端 SHA 只证明该版本已推送，不能写成已部署或现场通过 |

- 目标上的已确认失败仍按[合并阻塞](每日复盘.md#判断与处理)保持；任务分支通过只支持该候选。修复集成及目标上的必要验证完成后，才能解除目标阻塞。“已验证，待集成”不等于目标问题已解决；声明整项完成仍须满足用户要求的全部交付条件。
- **未改写提交的集成**：固定目标完整 SHA，用 `git -C <仓库> merge-base --is-ancestor <修复SHA> <目标SHA>` 核对可达性（0 可达、1 不可达，其他非零为检查失败）。`branch --contains` 可辅助定位。可达只证明历史包含，仍需核对目标最终内容及适用验证，防止后续撤回或覆盖。
- **squash／rebase／cherry-pick**：保留来源提交或范围、集成方式、对应的目标提交与完整目标 SHA；原提交不可达不能单独判为未集成。核对来源净差异与目标集成差异、受影响最终文件和冲突解决；一对多、多对一或混入其他改动时逐项说明映射。等价补丁的计算复用[错题本维护](每日复盘.md#错题本维护)，patch-id 相同仅为对应线索，不能替代最终内容与受影响行为验证。
- 目标引用新鲜度必须明确；未 fetch 时仅代表本地引用快照。`rev-list --left-right --count`、ahead/behind、提交说明或 `ls-remote` 单项均不能证明内容已正确集成。无法建立映射或目标内容与证据不符时写“集成未验证”，保留相应阻塞；不得为获得证据擅自改写历史或执行集成。
- 汇报：改动仓库、原分支与目标分支、提交哈希、推送结果、拉取结果、非本次残留改动；任务验收、分支推送、目标分支合入及原目录同步分别报告。
