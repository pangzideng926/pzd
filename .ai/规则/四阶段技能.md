# 四阶段方法：按需 SDD

触发：需要对齐需求、形成规格、拆分任务或按任务实施时按需读取。
本文件规定阶段目标与交付条件，不依赖已安装技能；不将四步变成每项工作的固定关卡。

## 入口与权限

- 根入口与 [工作原则](工作原则.md) 优先；简单任务可直接实现，信息足够时可从 Spec、拆票或实现阶段开始。
- 只执行用户请求的阶段；已明确的答案、测试边界和拆分要求直接继承，只有关键未决项才询问。
- 明确调用文档阶段即授权该阶段约定的本地文档写入；咨询“能否采用”不是调用，不写入。
- 不自动发布到外部追踪系统、不创建新聊天、不接着实施其他票。
- 按用户意图确定当前阶段，不因名称不同增加安装、配置或额外关卡。

## 唯一正文与发现

- 阶段目标、资料位置和完成条件以本文件及项目现行规范为准，已有计划、Spec 或 ticket 优先复用。
- 使用其他实现承接阶段时，入口只引用共享规范，不复制技能、规则或知识库，不依赖跨仓库边界自动继承。
- 本仓只维护流程约定。具体技能发现、安装位置及调用方式属于可选实现，缺少某个实现不妨碍直接完成同一阶段。
- 不自动安装、更新或改写项目入口；采用外部实现时核实其适用范围及与现行约束是否一致。

## 位置与约定

- 本节位置约定适用于共识、Spec 和 ticket：优先沿用目标仓库已经明确的文档/追踪配置，没有配置时使用 `docs/work/<功能标识>/`。开发计划独立遵循 [开发流程](开发流程.md) 的 `docs/plans/` 约定；阶段资料引用已有计划，不重复保存设计正文。
- 默认结构为 `共识.md`、`spec.md`、`tickets/01-<短名>.md`；按实际采用的阶段生成，绝不为凑流程补齐空文件，不自动迁移已有资料。
- 正式 Spec/ticket 纳入目标仓库版本管理；若被忽略或不允许入库，先说明并确定持久替代位置，不强行 add -f。
- 不把持久文档放 `.tmp/` 或当临时文件清理。跨仓库资料设一个主位置、各票注明所属仓库，不复制多份 Spec。
- 共识记“为什么/做什么/未决项”，Spec 记行为、约束、接口和测试契约，ticket 记本次可验收交付及证据；下游引用上游。
- 术语与 ADR 优先引用既有共享知识或项目正式文档；确有项目独有的新决定才在约定位置记录。共享可复用结论按 [知识沉淀](知识沉淀.md) 沉淀。
- 需要改变默认位置或追踪系统时，只在当前仓库已确认的统一规则入口（默认 `AGENTS.md`）补充差异/引用；各工具沿用现有共享入口桥接，不重复导入已经包含的项目正文。
- 不自动运行外部初始化步骤改写项目入口，也不扫描全部子仓库批量初始化。

## 四阶段契约

| 阶段 | 必要内容 | 可进入下一阶段的条件 |
|---|---|---|
| 对齐需求 | 目标、非目标、约束、成功标准、已确认决定、待决问题 | 阻碍设计的关键问题已有答案；假设单独标明 |
| 形成规格 | 问题/方案、可观察行为、重要边界、接口/状态/数据决策、验收编号、测试边界、非目标 | 阻碍实施的问题已解决；否则保留 draft 和待决清单 |
| 拆分任务 | 按功能纵向切片，每票独立文件，引用需求依据及基线，列依赖和验收 | 粒度与依赖已由本次指令或审阅确认；前置条件准确 |
| 实施验证 | 核对当前票、依赖和需求基线，实施验证、按需审查，提交前回填验收，执行 Git 收尾 | 验收证据充分；交付验收、Git 同步、部署状态分别说明 |

- Spec 使用版本标识或内容摘要加日期记录基线，验收条目使用稳定编号；有 Spec 的 ticket 引用同一基线。
- 从已确认计划或对话直接拆票时，在 ticket 中记录需求来源、已确认约束/验收的最小快照和来源日期或版本；不强制补建 Spec。
- 修改 Spec 的行为契约时只核对受影响的票，标记需重新确认/验证；不按旧 Spec 静默继续，不扫描全部历史。
- 新增关键未决项、依赖未完成、验收无法执行时，在正文记录受阻步骤，并按[任务状态与中断](开发流程.md#任务状态与中断)判定整票状态；不自行另定阻塞含义或猜测完成。
- 任务以可演示/可验证的端到端行为拆分；不机械按数据库/API/界面分别拆票，不为了便利增加无关预重构。
- 每票是边界明确、可独立验收的工作单元；票之间可以依赖。写入范围不冲突的独立步骤可以并行，依赖前置结果的步骤须先核对前置完成证据。

## 新会话接手的最小信息

每张 ticket 至少包含：
- 唯一标识（仓库/功能/票号）、仓库绝对路径、目标与非目标、需求依据及基线（有 Spec 则引用，无 Spec 则保存最小已确认需求快照）。
- 前置票及其完成证据、验收条目、对应测试/验证入口；阶段资料已有的长篇正文只链接。
- 第一行状态及主写入者、更新日期、下一步、交付状态和实施条件，统一按[任务状态与中断](开发流程.md#任务状态与中断)维护；旧票兼容与移交边界也以该节为准。
- 任务与仓库/worktree 映射以 [Git与worktree](Git与worktree.md#创建-worktree-与任务映射) 为唯一正文，写在 ticket 开头，跨仓每仓一行；拆票时尚未创建的路径、任务分支和 SHA 标“实施时填写”，不编造或提前创建。开始实现时核对并补齐实际映射；实现、验证、审查结果及遗留问题在任务分支提交前回填。
- 新会话未获指定任务路径时，按[任务发现与接手](协作与知识.md#任务发现与接手)定位候选，不从检索结果自动认领或实施其他票。

推荐新会话请求（将占位说明替换为真实值）：

```text
任务工作目录：映射中的实际工作目录/worktree 绝对路径（尚未创建时先提供原仓库路径并按开发流程建立映射）
实施任务：ticket 的完整路径或明确授权使用的 Issue URL
只完成这张票；先核对依赖和 Spec 基线，再实现、验证、审查和 Git 收尾。
```

裸编号 `01` 只有在仓库、功能及追踪位置已确定且唯一命中时才可使用；有歧义先问，不遍历所有仓库寻找。
阶段推进本身不要求新建会话；需要真实接力时提供已有任务的完整定位。新会话读取当前票、相关 Spec 片段和必要规范即可。

## 测试与完成

- 测试与验证按[开发流程](开发流程.md#验证)，审查按工作原则 D2，收尾与 ticket 回填按 [Git与worktree](Git与worktree.md#收尾已授权的固定动作)。
- 若确需 ticket 持久引用实现提交，只记录已存在的哈希，并在推送/切回前完成文档提交，避免循环补交。
- 前置票未完成、缺少本票必要验证证据或存在未决验收时，不标记当前票完成；开发流程规定的必需测试仍须实际执行，已实现但未部署必须明确。
- 结尾按[知识沉淀](知识沉淀.md)判断是否有新增可复用结论，不为每张票再生成重复总结。
