# 开发流程

触发：代码修改、测试、审查时读取。先遵循[工作原则](工作原则.md)。本文件是开发与验证证据细则的唯一正文；隔离、提交、推送与集成见 [Git与worktree](Git与worktree.md)。

## 定范围与计划

1. 按用户最近明确的目标和排除范围核对实际修改路径，再定位目标仓库绝对路径并读取必要规范（仓库 `docs/`、`.ai/项目/<项目>.md` 及既有约定），保留项目质量检查要求。“继续”“全部修复”等承接已明确的范围；审查材料、旧计划、规则来源目录或既有 worktree 只提供定位线索，不能自行替换目标。发现审查对象不在该范围时，先纠正问题归属，再到授权范围核实，不直接把改动写入审查对象。
2. 开发或修复前，从已确认资料根定位真实错题本，按当前项目＋模块＋错误类型／函数／字段／代码模式检索；本仓 [AI错题本](../知识库/AI错题本.md) 仅为空白格式参考。检索与来源核实见[协作与知识](协作与知识.md#读取与接手)；无命中不等于没有历史问题，不全量加载历史。
3. Git 项目按 [Git与worktree](Git与worktree.md#何时隔离) 判断是否需要隔离，取得实际工作目录；非 Git 项目确认实际目录与恢复方式，不为执行流程初始化仓库。
4. 以修改前后字段、含义和调用关系的实际差异，按下表确定三项要求，并在任务资料或首次实施说明中记录计划位置（需要时）、验证入口和审查方式。

需要隔离时，实际工作目录创建成功并核对归属、起点后，才写入计划与实现；需要计划时，计划保存成功后再实现。前置失败保留现场，仅继续无依赖调查或验证。

| 判定项 | 依据 | 实施要求 |
|---|---|---|
| 计划 | 改变接口或数据结构契约、跨模块调用链、多个模块/仓库或复杂功能 | 先在目标项目 `docs/plans/` 落盘计划，再修改实现；代码与配置、Git 与非 Git 项目同一标准 |
| 计划 | 契约稳定，修改限于单一局部 | 直接实施并执行相关验证 |
| 验证 | 高风险逻辑或反复回归缺陷 | 先证明失败再修复（见[验证](#验证)）；其他变更验证关键路径与失败路径 |
| 审查 | 复杂实现或关键业务逻辑 | 按工作原则 D2 独立只读审查；低复杂度、低风险由主代理核验 |

计划要求：

- 内容：目标、范围、责任文件、关键接口与依赖、决策、恢复方式、按可验收交付组织的步骤、验证对象与环境、风险。
- 初稿及后续状态按下节维护；步骤和验证以实际结果为准，已有计划直接更新。工具待办引用计划文件。
- 只展开影响判断的接口、算法和测试示例；不预写全部代码，不固定微步骤，不因操作步骤多就强制建计划。精简计划不降低验证与审查要求。
- 文档只为澄清、验收和接力服务，不强制 PRD/设计/实施套件；已有计划、Spec/ticket 优先更新或引用。四阶段按需采用，见[四阶段技能](四阶段技能.md)。
- 上下文压缩或任务恢复后，先重读未完成任务的计划；与实际不符时更新。

## 任务状态与中断

本节是计划、ticket 及必要的 `docs/work/<任务编号>/任务.md` 的唯一状态定义。新建或实际接手修改时，在文件第一行写 `状态：<固定值>`，随后写主写入者、更新日期（含时区）、下一步和交付状态；标题及正文接在任务头之后。不为纯咨询或局部单会话任务强制建文档。

```text
状态：待实施
主写入者：未认领
更新日期：YYYY-MM-DD HH:mm Asia/Shanghai
下一步：明确到可执行动作或待确认决定
交付状态：待收尾
实施条件：已具备／待满足的具体条件及来源
```

| 状态 | 含义与转移条件 |
|---|---|
| 待实施 | 约定范围尚未开工；实施条件区分已准备好与仍有缺口，不因文档存在或条件已齐而扩大实施授权 |
| 进行中 | 已认领且正在推进约定范围；记录可区分的人／会话和任务分支（如适用），进入前核对实施条件与写入范围 |
| 暂停 | 用户或任务负责人主动搁置，或明确停止执行等待接手；补充暂停依据、恢复条件，满足条件并核对授权后再恢复 |
| 阻塞 | 已进入获授权的执行或准备工作，但本记录范围内当前必要工作均被具体障碍阻断；写明原因及解除条件，不把单票或单仓阻塞扩大到全部任务 |
| 已完成 | 本任务约定验收已有充分证据，无未决验收；计划写完或文档修订完成不等于所规划的实施已完成 |
| 已取消 | 有明确取消决定，记录决定来源、未交付范围及替代任务（如有）；失败或暂时无进展不能据此取消 |

- 正文明确本次交付范围；“只交付设计”与“实施设计”分别判断。修订尚未实施的计划不自动认领或启动其业务任务；父计划由负责人按整体验收判断，引用各票／各仓结果，不机械汇总或覆盖分项状态。
- 尚在界定范围或实施条件、未进入获授权执行的记录保持待实施；不能仅因列明前置依赖就视为条件已具备。只有部分步骤受阻且仍有独立工作可推进时，任务按实际开工情况保持待实施或进行中，在正文保留受阻步骤及解除条件；整体无法推进才转阻塞。
- 主写入者未知时写“未记录（接手前确认）”，不能推定为无人认领。进行中的任务不被另一个会话重复认领；确需接力先明确移交。任务头不是跨机器的互斥锁，可见范围见[任务发现与接手](协作与知识.md#任务发现与接手)。
- 交付状态仅用 `待收尾 / 已收尾 / 不涉及`，汇总本次约定的交付动作；细项与证据按 [Git 状态判定](Git与worktree.md#状态判定)记录。验收已完成但所需推送、合并等未完成时仍为待收尾，下一步保留具体动作；只有用户要求的全部条件满足才可宣称整项交付完成，不给未要求的发布或部署制造待办。
- 中途明确停下、阻塞、移交或范围变化时，主写入者先按实际情况更新任务头和下一步；暂停补恢复条件，阻塞补解除条件，必要时注明未提交文件及工作目录。不必另建交接文件。普通轮次结束、存在未提交改动、时间较久或正在排查失败，不自动意味着暂停或阻塞。
- 暂停或阻塞时保留原主写入者，未认领或未知也保留原标记；他人接手先由原主写入者或用户明确移交。恢复时核对任务头、正文、仓库现场及条件，条件满足后按实际是否开工转待实施或进行中；尚未满足不能仅因新会话启动而改态。重新打开已完成任务时保留既有验收历史，写明新授权和受影响验收。结束、取消和中断时也据实更新交付状态。
- 旧票兼容读取：`in-progress / blocked / done` 分别对应进行中／阻塞／已完成；`draft / ready` 均属待实施，但分别保留“条件未齐／已齐”的依据，缺证据时记未知。旧自由文本或缺失字段列待核对，接手时再补齐，不扫描改写全部历史。Spec 的 draft 表示文档成熟度，不作为任务生命周期。
- 状态的提交、推送与跨设备认领遵循 [Git 状态检查点](Git与worktree.md#状态检查点)；非 Git 资料沿既有授权的持久位置，不为状态同步初始化仓库。

## 实施

1. **恢复依据**：按工作原则 D1 判断是否需要备份；需要时先备份并核对一致，再改写。恢复方式写入计划或任务说明。
2. **修改与检查**：按当前项目与实际环境的执行约束完成检查；失败保留为失败，修复后验证受影响项。
3. **记录证据**：按[验证证据分级](#验证证据分级)写入本次任务资料（计划或 ticket），不只留在对话。
4. **有边界的结论**：每项结果关联检查对象、执行环境和已检查行为；结论只覆盖证据支持的范围。计划记录、变更说明和最终回复复用同一份结果。

- 保护他人工作：同一文件存在混合改动时先辨别归属，不整文件覆盖、回滚或擅自 stash。

## 验证

- **必须先失败测试**：库存、数量计算、撤销回写、金额、权限、幂等、状态流转、反复回归缺陷。先写最小失败测试，确认因预期行为失败，再实现通过；即使只改一行。
- 测试约束可观察行为和重要边界；不测试实现细节，不为低影响文档配置凑测试。
- 新增或改变契约时，在计划或验收资料中对应“关键承诺 → 代表性正例／反例 → 验证入口”。兼容性承诺同时覆盖原行为；支持范围用实际使用的代表实现及边界验证，不以断言数量代替契约覆盖。
- 阶段内只执行与当前修改直接相关的验证。全部目标完成时，项目定义的完整验证必须覆盖最终候选；范围限于目标项目，不构建整个多仓库工作区。
- 修复缺陷时，用回归测试、最小复现、测试替身或等价模拟证明原问题已解决。
- 缺少测试环境时优先离线最小回归。无法完整复现实际环境时，分别说明直接验证、代码与证据推断、仍未验证的部分；无法复现不证明问题不存在或已解决。
- 无法完整验证时，说明未执行项、原因、替代验证和剩余风险。未运行不记为通过；不在生产制造失败；编译成功或单项通过不等于完整验证。
- 按实际层次报告：配置断言证明配置关系，模拟／替身证明模拟条件下的行为，真实运行才支持运行时或现场结论。
- 验收、审查、部署结果分开报告；本地通过不代表上线或现场验收。
- 审查的触发与范围见工作原则 D2；审查与 Spec 验收可以一次完成。

## 验证证据分级

按用途选用够用的最低级别；高级别包含低级别全部字段。证据只在已有计划、ticket 或项目验证记录中保存一份，交付与复盘引用它。

| 级别 | 适用场景 | 必记字段 |
|---|---|---|
| L0 日常 | 本地开发、阶段内验证 | 核验方法、实际动作、结论与未覆盖项；执行命令时记录完整命令及真实退出码 |
| L1 交付 | 提交、推送、ticket 回填、最终交付 | L0 ＋ 仓库、完整被测 SHA（未提交时写基线 SHA＋dirty＋受测文件清单及各文件 SHA256）、执行时间、原始输出位置 |
| L2 门禁 | 声明可合并、把旧证据复用到新候选、代码复盘 | L1 ＋ 时区、环境与相关工具／依赖版本、目标引用及当时解析的 SHA、dirty 指纹覆盖相关未跟踪代码、测试、依赖锁、配置与测试输入；必要时记录日志指纹 |

- 非 Git 文件没有提交 SHA 时明确“不适用”，以实际文件清单与 SHA256 绑定受测内容；无目标引用时同样标“不适用”，不伪造 Git 上下文。未知字段保持未知，不能当作不适用。
- 协作与文档复盘按[每日复盘](每日复盘.md#每日复盘执行任务)的来源、候选、核验方法及结果要求取证；包含代码合并或跨候选复用判断的部分仍按 L2，不能借任务名称降低门禁。
- 未执行的检查标“未运行”；历史报告不冒充本轮实测。不抄录凭据或敏感内容。
- 受测内容在运行期间变化、无法确认与记录一致时，保留原输出，但不能据此证明最终候选通过。
- 合并前必须证明必要检查适用于最终候选；证据缺失、无法对应候选或存在未解决的必要检查失败时，不得声明可合并。

### 证据复用

- 同一候选的已有结果直接沿用，不因进入收尾阶段重跑。补齐的字段必须取自同次执行的原始输出或日志；无法取证时保持原级别，不能靠推定升级。dirty 内容提交后，用 L1 文件清单与 SHA256 证明提交内容一致即视为同一候选。
- 只有 L2 记录可以复用到另一个候选。
- 可复用条件：当前候选、相关依赖、配置、测试输入、环境与目标上下文仍与受测条件一致；存在差异时，具体说明差异不影响该检查实际读取的输入（例如只改了该测试不读取的展示文案）。
- 不能只凭同一 SHA、同文件名、改动小或口头判断认定有效；无法证明时重跑受影响检查。整树指纹不同不自动要求全量重跑。
- 必须重跑受影响检查：代码、相关依赖、配置、测试输入或环境改变；目标分支改变带来集成影响；存在冲突解决或其他集成差异（验证实际合并结果）。
- 项目明确要求对最终候选／合并结果新执行的检查，按项目要求执行。
- 复用时另记：原记录位置、原执行时间、原被测 SHA 或指纹、本次核对时间、已核对差异及不影响依据、需重验项。本轮实跑与复用分别列明；局部证据不外推为整体、部署或现场通过。
- 消息或阶段变化本身不是重跑理由；也不能以避免重复为由跳过受影响或必要的检查。

### 失败与证据缺失

- 同一候选的失败记录可复用于定位，不必为换消息再制造同一失败；它不能支持修复后通过。
- 原日志路径失效时，可找回同次执行的完整副本并核对候选、命令、环境、结果及已有日志指纹；仅文件存在或同名不算恢复。
- 无法恢复必要证据时，重验或明确证据不足并阻止放行。缺日志本身不证明产品有 bug；已确认失败按[每日复盘](每日复盘.md#判断与处理)保持未解决。

### 环境探针与统一采集

本标题保留历史锚点；现行要求见下节，不要求使用指定探针或采集脚本。

### 执行环境与证据记录

- 仅在任务依赖的能力尚未确认、环境发生相关变化或已有访问／执行异常时，先核实最小必要条件；由实际承担验证的环境给出证据，不以另一身份或宿主的结果代替。
- 能力不足只阻塞依赖该能力的步骤，独立工作继续。可以采用当前授权范围内、能够证明同一要求的其他方法；不能修改权限、全局配置或验证口径来伪装通过。
- 记录本次实际核验方法、对象、输入范围、过程及结果，关联候选版本或文件指纹；运行命令时保留完整命令、真实退出码及原始输出。人工核对或场景推演应注明方法，不虚构执行记录，也不替代必须实跑的检查。
- 同一次证据只保存一份，计划、日报与交付引用它。记录格式和采集手段不自动授予 L1／L2，不证明输入依赖完整；失败、超时、采集不完整或输入变化仍如实保留。
- 正式交付引用的证据按下节保存；临时夹具、一次性产物按[文件整理](文件整理.md#文件存放)存放。

### 验证资料位置

- 以已确认资料根保存 `.ai/验证/<任务>/<执行日期>/`；独立项目默认自身，共享工作区项目沿既有位置，不从规则源仓或临时 worktree 推定资料根。真实任务记录不得写入公共规则仓或空白模板。
- 结论按需保存在一份验收记录或已有计划／ticket，原始输出与指纹放上述目录的 `证据/<运行标识>/`；同日多次执行使用不同运行标识，不覆盖旧输出。日期取实际执行日，已有的明确验证位置可保留引用，不为套格式批量搬迁，也不强制生成空报告。
- 同一次证据只保存一份；计划、ticket 和报告引用实际记录。人工核对、场景推演与真实运行分别标注，不因目录或文件名而升级证据级别。
- 已有证据确需迁移时按[文件整理](文件整理.md#每次整理如何登记)核对原始字节、登记旧新路径并更新直接引用；保留原执行时间和受测版本。历史日志内部旧路径不改写，迁移不是重新验证。仍被程序或工作树使用的文件保持原位，必要副本注明原件、同次执行与一致指纹。

## 首个业务闭环复核

新接入或流程实质变化后，在首个真实业务任务达到约定交付边界时，由任务负责人复用原验收记录核对需求、实施、验证、审查及 Git 交付是否衔接，有无重复步骤、歧义或遗漏。依据实际证据合并重复、澄清约束；一次未触发不能证明门槛无用，不削弱必要验证、权限和证据要求。

未发生真实业务使用时标“待首个业务任务验证”，规则静态检查或合成场景不能替代；待审批／集成等尚未经过的环节继续待观察。只在该任务或已触发复盘中执行，结果留实际项目资料，不新增调度、全工作区扫描或重复台账。

## 完成报告

- 简洁说明实际修改、关键设计决策、验证结果、尚未验证部分、剩余风险和 Git 提交；简单任务无需固定格式。
- 提交、推送、合入、部署、现场验收分别报告，判定方法见 [Git与worktree](Git与worktree.md#状态判定)；未要求或未执行的项如实注明。
