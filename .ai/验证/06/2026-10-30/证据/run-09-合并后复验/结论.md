## 三、四种业务态独立复核（用我自己的实体与表，不碰票面的 TestUser）

老卫要拿这四个 code 写交接、07/08/09/13 照着接，所以我不抄老登的数字，自己造了一遍：

| 探针 | 场景 | 实测 |
|---|---|---|
| M1 | 调用方拿「活跃快照」，库里已被别人软删 | `RecordInTrash` / **409** / `Persistence.Record.InTrash`；库里 `UserName=回收站`、`Version=2` 未被动过 |
| M1b | 实体自己带着 `IsDeleted=true` 去 `UpdateAsync` | 抛 `InvalidOperationException`，消息含 `RestoreAsync` |
| M2 | 更新一条不存在的记录 | `NotFound` / **404** / `Persistence.Record.NotFound` |
| M3 | 乙租户的行，用甲租户上下文更新 | `NotFound` / **404**（不是 403、不是 VersionConflict）；别家那行 `TenantId=2 UserName=别家 Version=1` 一字未改 |
| M4 | 版本被别人改掉 | `VersionConflict` / **409**；内存实体 `Version` 与 `UpdatedAt` 都保持调用前的值 |

**一条要写进交接的口径** ⚠️「更新回收站里的记录」有两种形态，返回值不同，交接不能只写一种：

- 实体带 `IsDeleted=true` 或 `DeletedToken≠0` → **抛 `InvalidOperationException`**（入口前置守卫，提示走 `RestoreAsync`）；
- 实体是干净的活跃快照、库里已删 → **返回 `RecordInTrash`/409**。

07/08 如果照「一律返回值」写调用方，碰到第一种形态会没有对应的处理分支。

## 四、过程中的两次自纠（说明探针不是随手写的）

我头两版 M1/M3 探针都是红的，红的都是我自己的构造错误，不是产品缺陷——记下来免得被当成新 bug：

1. 第一版 M1 把回收站实体（`IsDeleted=true`）直接丢给 `UpdateAsync`，被入口前置守卫先抛了异常；
2. 改掉 `IsDeleted` 但 `DeletedToken` 还是非 0，又被第二道守卫（回收站误用）拦下；
3. M3 第一版用租户 1 的客户端插 `TenantId=2` 的行，撞上插入租户守卫（正是 P2 修的那条）。

三处都是**守卫有效**的旁证：要打到我想要的那条路径，必须先把实体构造成干净快照。
