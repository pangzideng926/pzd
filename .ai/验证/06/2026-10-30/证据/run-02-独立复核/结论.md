## 二、两处「没照票面抄」的决定：我用实验替他兜住

### 1. 软删除唯一索引用 `DeletedToken` 而非 NULL——**票面原方案确实是漏的**

我在真库上做 A/B 对照（`pzd_test_` 前缀，用完即删）：

| 方案 | 两条同名活跃记录 | 软删除后同名重建 |
|---|---|---|
| **A 票面原方案**：`DeletedToken BIGINT NULL`，未删除为 NULL | **两条都插进去了，`COUNT(*)` = 2** | — |
| **B 雨哥方案**：`DeletedToken BIGINT NOT NULL DEFAULT 0` | 第二条被拒：`ERROR 1062 Duplicate entry '1-王五-0' for key 'u.ux'` | 软删除写 `DeletedToken=Id` 后重建成功，`COUNT(*)` = 2 |

**A 方案下唯一约束等于不存在**，这不是理论问题——MySQL 唯一索引对 NULL 不去重，实测复现。雨哥的改动方向正确，`(TenantId, 业务键, DeletedToken)` + `0/NULL` 换成 `0/自身主键` 能同时满足「活跃唯一」与「删除后可重建」。这条我会在交接里强调：**17 号票照抄时别再照票面旧文字**。

## 三、⚠️ 需要老何定性的一条（medium）：写入口没有租户谓词

`PersistenceWriter.UpdateAsync` 生成的 SQL 是：

```sql
UPDATE `{表}` SET … , `Version`=`Version`+1 WHERE `Id`=@id AND `Version`=@version
```

**WHERE 里没有 `TenantId`。** 票面写「本票只按单库单连接验证，租户库切换归 07」，但 `pzd_master` 是共享库、所有业务表都有 `TenantId` 列——也就是说：**只要知道别家租户的 `Id`，06 的写入口就能跨租户改掉那条记录**（版本号对得上就成功）。

我没有把它写成失败用例，因为当前仓库里还没有「租户上下文」这套东西（07 才做），硬造一个会变成我替 07 定接口，那是越界。但这属于「租户隔离」这一类必须测试先行的规则（AGENTS.md 明列），请老何在 07 或 19 的票面里明确一句，二选一：

- **A：租户谓词归 06**：`UpdateAsync` 增加租户参数并进 WHERE，06 补一条「A 租户上下文写不到 B 租户同 Id 记录」的用例（这条我能立刻写出来并跑红）；
- **B：租户谓词归 07/19**：那就在 06 票面写清「本入口不做租户隔离，07 之前不得在生产路径使用」，并给 07 立一条硬前置——否则 06 的写入口会成为默认写法被后续票照抄。

现在票面里只有「租户库切换由 07 号票」，说法是**分库**，没覆盖**同库多租户**这种情形，容易让人以为租户隔离已经有人管了。
