## 3. 本轮发现

### medium 1 · 官方插入入口能造出「删除态但 `DeletedToken=0`」的幽灵行，永久占住唯一键

- **文件与行**：`src/Pzd.Infrastructure/PersistenceAudit.cs:100-102`（`OnInsert` 的 `DeletedToken` 分支无条件 `entity.SetValue(0L)`；插入侧没有任何「删除态」校验）
- **探针原文**：

  ```
  C11 InsertAsync(IsDeleted=true)：failure=null；库里 IsDeleted=1 DeletedToken=0 DeletedBy=0 DeletedAt为NULL=1 Version=1
  C11 随后同名活跃插入：failure=DuplicateKey；活跃记录数=0；物理行数=1
  ```

- **问题**：`PersistenceWriter.InsertAsync(db, new X { IsDeleted = true })` 会成功，写出一行「删除态」但四列删除审计一个都没写全的记录。这行**应用侧查不到**（软删除全局过滤器挡着），却**占着唯一索引** `(TenantId, 业务键, DeletedToken=0)`：同名记录再也建不出来，直接返回 `DuplicateKey`（09 映射 409），调用方只会看到「已存在」，但列表里没有、回收站里也没有。
- **为什么错**：这和 high 5 要消灭的 `TenantId=0` 幽灵行是同一类缺陷——**用官方入口造出了业务语义上不存在的行**。票面「对外契约」写死「软删除只走 `SoftDeleteAsync`」，而插入侧留了一条把实体直接插成删除态的路，四列没有一次写全，而 `DeletedToken=0` 又正好撞上活跃记录的 token 值。另外这行就是 medium 2 能复活的那类行，两条互相喂。
- **修改建议**：`OnInsert` 里对 `IsDeleted` 加校验——实体 `IsDeleted=true` 时**抛** `InvalidOperationException`，消息写明「插入不接受删除态实体，请先 `InsertAsync` 再 `SoftDeleteAsync`」。这样「删除态」只可能由 `SoftDeleteAsync` 产生，四列必然齐全。（备选：按完整删除态写全 `DeletedToken=Id / DeletedAt=now / DeletedBy=当前用户`，但那样「插入即删除」成了合法语义，更像给 07/08 留后门，不推荐。）补一条用例：`插入删除态实体被拒绝`。

### medium 2 · `UpdateAsync` 能把 `token=0` 的删除行改回活跃，留下删除审计残留

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:156-166`（守卫只按 `DeletedToken != 0` 判断）
- **探针原文**：

  ```
  C9 存量删除行(token=0) 走 UpdateAsync：failure=null（未拦）；库里 IsDeleted=0 DeletedToken=0 DeletedAt残留=1 DeletedBy=5 Version=2
  ```

- **问题**：把一行「`IsDeleted=1` 且 `DeletedToken=0`」的记录读取出来（`ClearFilter`），把 `IsDeleted` 置回 `false` 再调 `UpdateAsync`，守卫放行——结果是一行 `IsDeleted=0` 但 `DeletedAt/DeletedBy` 还留着的**活跃记录带删除审计**。`token=0` 恰好是「活跃」的标记值，所以它既不复用回收站的 token 语义，也不会被唯一索引挡住。
- **为什么错**：票面契约写死「恢复只走 `RestoreAsync`」，而这里留了一条复活路；`RestoreAsync` 辛苦维护的「token 归 0 + `DeletedAt/DeletedBy` 清空」被这条旁路破坏。上一轮的守卫堵住了「正常软删除行」（token=Id），但**只堵住了这一种形态**——正是张一一反复点的「兜底把该挡的放过去」。`token=0` 的历史行不需要构造，medium 1 那行就是现成的。
- **附带发现（同一根因）**：`C10` 显示对删除态记录走 `UpdateAsync` 会把 `DeletedAt/DeletedBy` **刷新成当前时间与当前人**（`Version 2→3`），回收站按 `DeletedAt` 排序时这行会被顶到最新——「改一份已删记录」不该改删除时间。
- **修改建议（根除，推荐）**：`WriteKind.Update` 的 SET 里**不写 `IsDeleted`**——把它当不可变列，`IsDeleted` 的 true→false 只能经 `RestoreAsync`、false→true 只能经 `SoftDeleteAsync`。这样上面两条一起消失，也不需要「猜当前行是不是删除态」。代价：现用例 `UpdateAsync带IsDeleted时也写全删除审计` 的语义要改成走 `SoftDeleteAsync`（那才是它真正想验的东西），`ValueFor`/`ApplyUpdateStamp` 里 `Update` 种类不再产出删除四列。
- **备选（最小改，不推荐）**：守卫条件再加 `|| DeletedAt is not null`。能挡 C9 这次的形态，但「`token=0` 且 `DeletedAt=NULL`」的第三种植还漏（`C11` 造出来的就是这种），属补丁不治根。

### low 1 · `ReadBool` 留着一段无意义 `switch`（像是变异脚本没回退干净）

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:247-253`
- **问题**：

  ```csharp
  private static bool ReadBool<T>(EntityInfo info, T entity, string propertyName)
      where T : class
      => ReadLong(info, entity, propertyName) switch
      {
          _ => info.Columns.SingleOrDefault(current => current.PropertyName == propertyName)
              ?.PropertyInfo.GetValue(entity) is true,
      };
  ```

  `switch { _ => … }` 只有一条恒命中分支：输入值（`ReadLong`，一次反射查找 + 一次反射取值）算出来后**直接丢弃**，分支体又自己重新查一遍列。行为与原来的单行表达式完全等价。
- **为什么错**：纯冗余，读代码的人会以为「`ReadLong` 的结果参与了判断」而去找不存在的耦合；也可能是某次变异实验的残留没退回干净——这类残渣会让人怀疑同一提交里还有别的残渣。
- **修改建议**：改回 `=> info.Columns.SingleOrDefault(current => current.PropertyName == propertyName)?.PropertyInfo.GetValue(entity) is true;`（`ReadLong` 保留给它真正的调用点用）。

### low 2 · `SetColumns形态的旁路也被拒绝` 的注释已过期，与用例代码自相矛盾

- **文件与行**：`tests/Pzd.IntegrationTests/PersistenceTests.cs:321-323`（注释）对 `:325-328`（用例代码）
- **问题**：注释写「不带版本条件的 `Updateable` 连 `Version` 都是 0，直接拒绝」，而用例里显式写了 `SetColumns(it => new TestUser { IsDeleted = true, Version = 1 })`。
- **为什么错**：拦截现在是无条件的（这正是 high 1 的修法），注释却仍在解释上一版「只拦 `Version<=0`」的口径；照注释读会得出「设 `Version=1` 就能过」的错误结论——下一轮谁来做变异，很可能照着注释去验证一个已经不存在的机制。
- **修改建议**：注释改成「`UpdateByObject` 现被无条件拒绝；本条证明 `SetColumns` 这条不带实体的旁路也走不通」，并说明「漏写 `DeletedToken` → 1062」的代价路径已不可达。
