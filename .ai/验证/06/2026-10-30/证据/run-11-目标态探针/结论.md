**2 条红是故意的**：它们是「改造后目标态」，现在红就是「改造还没落地」的证据；改造落地后必须转绿，任何「只改枚举/注释、行为没变」的做法都会让它们继续红。

## 二、两条红（目标态，实测输出）

```
[目标态1] Kind=VersionConflict Code=Persistence.Record.VersionConflict
          msg=记录已被其他操作修改，请刷新后重试。      ← 期望 NotInTrash + 「不在回收站」
[目标态2] caught=InvalidOperationException 活跃记录=0   ← 期望恢复成功、活跃记录 1
```

断言写的是**目标**而不是现状：

- 目标态一：`Code == "Persistence.Record.NotInTrash"`、`HttpStatusCode == 409`、文案含「不在回收站」、文案**不含**「刷新」；
- 目标态二：不抛异常、恢复后活跃记录为 1。

两条都同时校验 code 与文案——这正是第 6 行那个错「只比 code 看不见」的教训。

## 三、一条稳定项（防改造时把版本校验弄丢）

```
[稳定] Kind=VersionConflict Code=Persistence.Record.VersionConflict
       库里IsDeleted=1 （库里Version=2，实体拿的是1）
```

「目标已删、但实体拿的是删除前的旧版本号」→ 现在 `VersionConflict`，且库里仍是 `IsDeleted=1`（没有被误恢复）。改造改成库判定后这条**必须保持绿**：如果为了区分「在不在回收站」而把版本条件从 WHERE 里拿掉，这条会立刻红。

## 四、文案快照（新增，钉住「用户看到什么」）

```
InTrash         → Persistence.Record.InTrash          | 这条记录已被删除，如需修改请先恢复（RestoreAsync）。
NotFound        → Persistence.Record.NotFound         | 记录不存在，或不属于当前租户。
VersionConflict → Persistence.Record.VersionConflict  | 记录已被其他操作修改，请刷新后重试。
```

三条两两不同、都非空。这条探针的价值不在现在（全绿），在**将来**：谁改了任何一句文案，这里立刻可见，而不是等审计读 SQL 才发现。
