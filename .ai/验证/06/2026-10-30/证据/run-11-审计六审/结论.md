## 1. 五审两条的闭环证据（我自己跑的）

```
Q1 脱离实体更新已删除记录：抛 System.InvalidOperationException；库里 IsDeleted=1 UserName=脱离 Version=2
Q2 更新后：failure=null；库里 DeletedAt为NULL=1 DeletedBy=0 IsDeleted=0 Version=2
Q2 更新后：内存 DeletedAt=2020-01-02T03:04:05.0000000Z、DeletedBy=5、Version=2
```

- **P8 已闭环**：`WHERE` 的 `AND IsDeleted=0` 是真正的防线——实体不带任何删除标记也能挡住（内存里两道守卫对此无效），并且拒绝后库里的业务字段与版本一个都没动。
- **P4 按裁定闭环**：内存实体保留调用方塞的脏值（不擦、不回查库），库保持 `NULL/0`。这是张一一的决定，我认可这个取舍方向（为一个不该出现在响应里的字段多打一次 SQL 不划算），但它带来一个副作用——见 medium。

## 2. 本轮发现

### high · 三种情形在 06 侧**不可区分**，09 票要求的三个 code 落不了地

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:255-268`（`affected == 0` 只区分「在回收站」与「其余一律 `VersionConflict`」）、`:311-334`（`IsRecycledAsync` 只回答「是不是在回收站」）；票面 `docs/work/cross-cutting/tickets/06-persistence-base.md:265-271`（三种情形表达口径表）与 09 票 `:48`（`7fa5f54`，origin/main）新增条款
- **探针原文**：

  ```
  Q3 版本被改掉：failure=VersionConflict
  Q4 记录不存在：failure=VersionConflict
  Q7 别家租户的已删记录：failure=VersionConflict
  Q5 重复软删除：failure=VersionConflict
  Q1 脱离实体更新已删除记录：抛 System.InvalidOperationException
  Q8 无租户上下文：抛 System.InvalidOperationException
  ```

- **问题**：09 票写死「06 的 `PersistenceWriter` **已能区分三种情形**——版本被别人改掉、记录在回收站、记录不存在或不属于当前租户；09 要给出三个互不相同的 `code` 与状态码」。实测只有**两种可判定输出**：

  | 情形 | 06 实际输出 |
  |---|---|
  | 版本被别人改掉 | `PersistenceFailureKind.VersionConflict` |
  | 记录不存在 | `PersistenceFailureKind.VersionConflict`（同一个值） |
  | 记录不属于当前租户 | `PersistenceFailureKind.VersionConflict`（同一个值） |
  | 记录在回收站 | 抛 **裸** `InvalidOperationException` |

  而 `InvalidOperationException` 在 06 里还承载「没有租户上下文」（Q8 实测同类型）、「缺主键/版本列」、「拒绝物理删除」、「插入删除态实体」等一堆**编程错误**。09 若按异常类型映射，会把编程错误一起当成业务态；若只映射 `PersistenceFailure`，就漏掉回收站。

- **为什么错**：这正是张一一在 09 票里点名要避免的坑——「把已删压成 409，前端提示刷新重试，而重载永远读不到」。现在 06 交出去的信号里，「不存在」与「版本冲突」一模一样，「回收站」又与编程错误同型，09 只能靠猜或字符串匹配（拿异常 Message 做判断），两张票的契约定不下来。属典型的「票面与代码两处说法并存」。
- **修改建议**（改动很小、可测）：
  1. `PersistenceFailureKind` 增加两个成员：`NotFound`、`RecordDeleted`；
  2. 把 `IsRecycledAsync` 换成一次查询返回三态——`SELECT Id, IsDeleted FROM <table> WHERE Id=@id AND TenantId=@t`：无行 → `NotFound`；有行且 `IsDeleted=1` → `RecordDeleted`；有行且 `IsDeleted=0` → `VersionConflict`；
  3. 业务态一律走返回值，**不再用裸 `InvalidOperationException` 表达**（编程错误继续用 IOE），这样 09 能干净地映 409 / 404 / 410 三个 code；
  4. `SoftDeleteAsync` 命中的是已删除行时返回 `RecordDeleted`（Q5 实测现在是 `VersionConflict`，对幂等 DELETE 语义是误导——`DELETE` 重复调用不该报并发冲突）；
  5. 四条用例分别钉住四种输出：`更新不存在记录返回NotFound`、`更新回收站记录返回RecordDeleted`、`重复软删除返回RecordDeleted`、`版本冲突仍返回VersionConflict`。只有这一组能证明「三情形可分」。
  6. 若张一一仍坚持「回收站用抛」，那至少要换成**专属异常类型**（如 `PersistenceRecordDeletedException`）并同步 09 票，否则 09 只能靠异常类型猜。

### medium · 本轮为 P4 加的 `touchDeleteColumns` 是**死参数**，配套用例**不可能失败**

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:278`（`ApplyUpdateStamp(entity, stamp, touchDeleteColumns: kind != WriteKind.Update)`）+ `src/Pzd.Infrastructure/PersistenceAudit.cs:209-224`；用例 `tests/Pzd.IntegrationTests/PersistenceTests.cs:717-745`（`UpdateAsync不改动内存实体的删除审计列`）
- **证据**：我把参数改成恒 `true`（等价于「Update 照旧回写删除四列」），结果——

  ```
  [M3-touch-delete-columns] TEST_EXIT=0  Total: 31, Failed: 0     ← 全绿，用例没红
  ```

  作为对照，我另做了一处**改 SET 列表**的变异（让 `Update` 重新往库里写删除四列）：

  ```
  Total: 31, Failed: 1    UpdateAsync不改动任何删除审计列 [FAIL]   ← 这条才是真防线
  ```

- **问题**：`stamp` 里的删除四列在 `Update` 路径上**恒等于实体自身的值**——守卫已保证 `IsDeleted == false`、`DeletedToken == 0`，而 `DeletedAt/DeletedBy` 本来就是从实体上读出来的（`PersistenceAudit.cs:204-205`）。所以「回写」与「不碰」结果完全一样，`touchDeleteColumns` 不产生任何可观察差异，那条新用例断言的正是「不管怎么实现都成立」的事实，**是一张空网**。
- **为什么错**：这条用例和这个参数的存在会让下一个人以为「内存侧一致性已被守住」，而实际上它任何实现都能通过。变异能红才算证据——雨哥报的「`Update` 也回写删除列 → `UpdateAsync不改动内存实体的删除审计列` 红 1 条」这句**与我的实测不符**：能红到的是「库不动」那条（`UpdateAsync不改动任何删除审计列`），不是内存这条。这不是他撒谎，是两处改动共用一个说法，把红的地点记错了。
- **修改建议**（二选一，都要写进票面）：
  - **A（最小）**：删掉 `touchDeleteColumns` 参数与那条空网用例，在票面把「Update 不回写内存删除四列」改成一句**事实说明**——「`stamp` 的删除列在 Update 路径上就是实体自身值，故内存侧无需额外处理」，别留一个假装在干活的开关；
  - **B（让参数有意义）**：`Update` 路径上把四列显式**归零/置 NULL**（也就是按「库里的真实值」写内存，`false / 0 / null / 0`），这时参数才真的改变行为、用例才能红。代价是多写四行赋值，不查库。

  我倾向 A（承认等价、删掉噪音），但 B 能顺带消掉 P4 那条「内存与库分叉」的观感问题，由张一一定。

### 记录在案（不新增要求）

- **P4 的残留分叉是已裁定接受的**：正常路径上从库里加载的实体本来就带活跃态常量，不碰即一致；只有调用方自己塞脏值时才不一致（`Q2` 实测内存留 2020、库为 `NULL/0`）。序列化层不输出这四列即可。已与张一一的口径一致。

- **`DeletedAt` 必须可空**（`OnInsert` 现在无条件 `SetValue(null)`）：这已是隐含硬约束，票面只在这轮 low 里提过一句，建议在「建表时必须带的约定」里补一句「`DeletedAt` 必须 `DATETIME(6) NULL`」，免得下游实体声明成非空后在反射里炸。
