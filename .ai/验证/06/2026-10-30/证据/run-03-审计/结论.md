## 三、发现明细

### high 1｜`PersistenceWriter.UpdateAsync` 把 `CreatedAt/CreatedBy` 一起写进 SET，更新会抹掉创建审计

- 文件：`src/Pzd.Infrastructure/PersistenceWriter.cs:37-46`
- 问题：`foreach (var column in info.Columns)` 除了主键和 `Version`，**所有列**都进 SET，包括 `CreatedAt`、`CreatedBy`。
- 为什么错：架构 §5.3 规定审计四列由 AOP 自动填充，`CreatedAt/CreatedBy` 是「谁在什么时候创建」的不可变事实。分离实体（只带 Id/Version/业务字段）或投影装载的实体走这条写路径时，会把这些默认值原样写回库。实测（探测 P1）：

  ```
  P1 插入后 CreatedAt=2026-10-30T01:54:47.8681470 CreatedBy=7
  P1 UpdateAsync 返回 failure=null（更新成功）
  P1 更新后 CreatedAt=1900-01-01T00:00:00.0000000 CreatedBy=0 UserName=改过
  ```

  不报错、不冲突、返回成功，审计痕迹被静默改写。
- 修改建议：SET 里排除 `CreatedAt`、`CreatedBy`（与主键、`Version` 同样跳过）；若确实要支持「全字段覆盖写」，另开一个显式方法名（如 `OverwriteAsync`）并在 XML 注释写清它会覆盖创建审计。

### high 2｜写入口没有租户谓词，且 SET 含 `TenantId`，可跨租户改写并「搬走」记录

- 文件：`src/Pzd.Infrastructure/PersistenceWriter.cs:55-57`
- 问题：`UPDATE … WHERE Id=@id AND Version=@version`，没有 `TenantId`；SET 又把 `TenantId` 当普通列写回。
- 为什么错：`pzd_master` 是共享库，每张表带 `TenantId`。只要持有 `Id` 与当前 `Version`（列表接口、日志、前端回传都能拿到），就能改写别家租户的记录，并把整行搬到自己的租户名下。实测（探测 P4）：

  ```
  P4 failure=null（更新成功）；之后 TenantId=2 UserName=乙租户改写
  ```

  07 号票已把「二选一」写进验收（`18c4458`），但那是**下游兜底**，06 是定这条 SQL 的地方。
- 修改建议（推荐 A）：`PersistenceWriter` 增加租户参数（`options.CurrentTenantId` 或方法参数），`WHERE` 加 `AND TenantId=@tenantId`；租户上下文缺失时**抛异常**而不是静默按 `Id` 更新。这样 07 只需供给值，不用回来改 06 的 SQL。若走 07 的方案 ②（写禁令），必须在 06 票面加显式禁令段落，「07 之前不得用于任何生产路径」不能只活在 07 票里。

### high 3｜软删除约定没有强制点：`Deleteable` 直接物理删，`SetColumns` 形态不写 `DeletedToken`

- 文件：`src/Pzd.Infrastructure/PersistenceAudit.cs:88-96`（只有 `UpdateByObject` 回调会写 token）、`PersistenceSoftDelete.cs`（只有读侧过滤，写侧无守护）
- 问题：软删除靠「调用方自己把 `IsDeleted` 置 true 再更新」。以下两种常见写法直接失效：
  1. `db.Deleteable(entity)` → 物理删除。实测（P2）：`Deleteable 影响行=1；真 SQL 物理行数=0`，`IsDeleted=0`。
  2. `db.Updateable<T>().SetColumns(it => new T{ IsDeleted = true })` → `DeletedToken` 仍是 0。实测（P3）：`DeletedToken=0`，随后同名重建 `Duplicate entry '1-王五-0'`。
- 为什么错：架构 §5.3 承诺「软删除 + 回收站可恢复」。物理删除后回收站永远恢复不了，且没有任何报错或日志；`SetColumns` 那条则让本票最核心的 AC（软删除后同名可重建）在最自然的写法下变成 1062，错误信息完全指不到根因。
- 修改建议：给写侧加一个强制点二选一——①在 `Attach` 里处理 `DataFilterType.DeleteByObject`，把物理删除改写成软删除（或直接抛异常提示必须走软删除入口）；②提供唯一的 `SoftDeleteAsync<T>(db, entity)` 入口，并在票面写死「软删除只能经由该入口或 `Updateable(entity)`」，同时补「`SetColumns` 形态不写 token」的反向用例，让下一个人知道边界在哪。另外建议补两条用例：`Deleteable` 不得物理删除、软删除后重建在两条入口上都要绿。

### medium 1｜架构 §5.3 要求 `DeletedAt/DeletedBy`，实现只有 `DeletedToken`

- 文件：整个 `src/Pzd.Infrastructure`（`grep -rn "DeletedAt\|DeletedBy" src/ tests/` 零命中）
- 问题：架构原文是「`IsDeleted` + `DeletedAt/DeletedBy`，全局 `QueryFilter` 过滤；回收站可恢复」，实现换成了单一 `DeletedToken` 方案。
- 为什么错：换方案本身可以接受（`DeletedToken=Id` 确实解决了 NULL 唯一索引漏判，这点我认可），但**删除时间与删除人丢了**：回收站无法按删除时间排序、无法显示「谁删的」，而 `PersistenceAudit` 自己的注释里还写着「回收站按时间排序时会出错」——注释与实现自相矛盾。决策笔记也没把这次替换记为「决定被取代」。
- 修改建议：要么按 §5.3 补 `DeletedAt DATETIME(6) NULL` + `DeletedBy BIGINT`（不影响唯一索引，`DeletedToken` 仍保留），要么由老何按决策笔记流程写明「§5.3 的 `DeletedAt/DeletedBy` 被 `DeletedToken` 取代」并说明回收站的排序依据。二者必居其一，不能两处说法并存。

### medium 2｜雪花主键 `WorkerId=1 / DatacenterId=1` 是写死常量，多副本部署会撞主键

- 文件：`src/Pzd.Infrastructure/PersistenceAudit.cs:57`（`SnowFlakeSingle.Instance.NextId()`），配置入口 `PersistenceOptions` 未暴露 worker 配置
- 问题：实测反射 `IdWorker` 得到 `WorkerId = 1`、`DatacenterId = 1`，全进程固定。
- 为什么错：模块化单体一旦起两个副本（Aspire 多实例、蓝绿、灰度共存），两个进程同一毫秒会生成**相同 Id**，表现为插入 1062 或主键冲突偶发——这类故障最难查，且 17/19/20/23/32 全部复用这套主键约定。
- 修改建议：`PersistenceOptions` 增加 `WorkerId`/`DatacenterId`，在 `CreateClient` 里设置 `SnowFlakeSingle.Instance` 对应值；值由部署配置给（实例序号），缺省时至少在启动期打警告。单实例本票环境看不出问题，但约定一旦被下游照抄就扩散了。

### medium 3｜版本冲突时内存实体已经被改写，失败不干净

- 文件：`src/Pzd.Infrastructure/PersistenceWriter.cs:33`（`ApplyUpdateStamp` 在 SQL 执行前）与 `:59-62`（`affected == 0` 直接返回）
- 问题：`UpdatedAt/UpdatedBy`（以及 `IsDeleted=true` 时的 `DeletedToken`）在执行 SQL 之前就写进了调用方实体；命中版本冲突返回 `VersionConflict` 时，这些值不回滚。
- 为什么错：调用方拿到 409 后常见做法是「重新加载再重试」，但此时手里的实体已经不是加载时的状态；若有代码基于实体做乐观重试或把它再保存一次，会把错误的审计时间带进下一次写入。
- 修改建议：先算好时间戳到局部变量，`affected > 0` 之后再 `Set` 到实体；或者冲突时把三个字段恢复原值。
