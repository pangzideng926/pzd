## 一、逐行实测（输出摘自 matrix.log）

| 行 | 入口 × 实体状态 | 老卫表里写的 | 实测 |
|---|---|---|---|
| 1 | `UpdateAsync` × 实体 `IsDeleted=true` | 抛 | **抛 `InvalidOperationException`**：`…处于删除态，不能用 UpdateAsync 更新…` |
| 2 | `UpdateAsync` × 实体 `IsDeleted=false` 但 `DeletedToken≠0` | 抛 | **抛 `InvalidOperationException`**：`…仍在回收站里（DeletedToken 不为 0）…` |
| 3 | `UpdateAsync` × 干净活跃快照、库已删 | 返回 `RecordInTrash` | `RecordInTrash` / 409 / `Persistence.Record.InTrash` |
| 4 | `SoftDeleteAsync` × 重复软删 | 返回 `InTrash` | `RecordInTrash` / 409 / `Persistence.Record.InTrash` |
| 5 | `RestoreAsync` × 实体自称活跃（DTO 形态） | 抛 | **抛 `InvalidOperationException`**：`…没有处于软删除状态，无法恢复。` |
| 6 | `RestoreAsync` × 实体说删但库活跃 | 返回 `VersionConflict` | `VersionConflict` / 409 / `Persistence.Record.VersionConflict`，库里 `IsDeleted=False Version=1` 未动 |
| 正路 | `RestoreAsync` × 正常恢复 | — | `failure=null`，活跃记录 1、`IsDeleted=False`、`DeletedToken=0`、`Version=3` |
| 文案 | 三种 409 | 「必须互不相同」 | 三条文案两两不同（见下） |

六行的行号与判定**全部对得上**，老卫读代码读准了。

## 二、第 5 行就是 09 会冒 500 的那条（实测钉住）

DTO 从 HTTP 体转回来的实体 `IsDeleted` 默认 `false`，`Id` 与 `Version` 都对，调 `RestoreAsync` 得到的是**异常**而不是返回值：

```
[行5] caught=InvalidOperationException msg=类型「ProbeUser」的这条记录没有处于软删除状态，无法恢复。
```

09 若按「一律返回值」写，这条会以 `InvalidOperationException` 冒成 500，而用户实际只是点了个「恢复」。张一一裁定「改库判定」是对的，这条就是它的必要性证据。

## 三、第 6 行的 code 是 `VersionConflict`——code 对，**但文案是错的** ⚠️

```
[行6] Code=Persistence.Record.VersionConflict
      msg=记录已被其他操作修改，请刷新后重试。
```

「恢复一条本来就没删的记录」被翻译成「记录已被其他操作修改，请刷新后重试」：用户刷新一百次也不会变。这不是「制度不完善」，是**明确告诉用户去做一件无用的事**。

两点建议：

1. 张一一裁定的 `NotInTrash` 正好治这一行，改造后文案是「该记录不在回收站」——比现在的通用并发文案准确得多。这条实测可以作为「为什么必须加第五种 code」的证据，而不只是「补一个 code 更整齐」。
2. 交界面的六行矩阵若只写 code 不写文案，读者会以为第 6 行真是并发场景。建议矩阵加一列「用户看到什么」，第 6 行改造前那格就是「请刷新后重试（误导）」。

## 四、三种 409 文案（实测原文）

```
VersionConflict = 记录已被其他操作修改，请刷新后重试。
InTrash         = 这条记录已被删除，如需修改请先恢复（RestoreAsync）。
NotFound（404）  = 记录不存在，或不属于当前租户。
```

三条确实互不相同，老卫写死这条要求没问题。补一条观察：`VersionConflict` 是唯一一条会被「非并发场景」复用的文案（第 6 行、以及 `UpdateAsync` 干净快照 + 版本不匹配），只要第五种 code 落地，它就能收窄回真正的并发语义。

## 五、给老卫的结论

- 六行矩阵**逐行实测成立**，可以放心留；行号与「抛/返回」的判定全部正确。
- 第 5 行建议标注「09 必须兜 `InvalidOperationException`」，现状下这是唯一会冒 500 的形态。
- 第 6 行建议加文案列并标注「现状文案误导，改造后归 `NotInTrash`」。
- 改造落地后，第 1、2 行按张一一的裁定要合并成「返回 `NotInTrash`」——我这套探针（`WriteEntryMatrixProbes.cs`）可以直接拿来改三行断言复跑，验它是不是真变了。
