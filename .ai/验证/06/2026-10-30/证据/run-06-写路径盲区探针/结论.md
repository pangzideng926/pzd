## 分级与定性

### high｜P4 + P5：写入口是「约定」，不是「强制」——老登 high 1/2/3 的旁路复活

`PersistenceWriter` 自己确实守得很好（`WHERE Id AND Version AND TenantId`、不可写列、冲突不脏实体）。但同一个 `SqlSugarClient` 上：

- `db.Deleteable<ProbeUser>().Where(it => it.Id == x)` —— **不带实体**，AOP 的 `DeleteByObject` 根本不触发，物理删一路通到 `物理行数=0`，回收站彻底失效。而 `db.Deleteable(entity)` 那条是被拦住的（06 票用例已覆盖）。两种写法在 SqlSugar 里都是惯用形态，差别只在「手边有没有实体对象」。
- `db.Updateable(intruder)` —— 只按主键更新：跨租户写穿（`TenantId` 1→2，整行搬走）、`CreatedBy` 抹成 0、`Version` **不自增**（1→1，乐观并发完全失效）。

这不是新发现的三个 bug，而是**同一批 bug 换了条路**：high 1（审计字段被抹）、high 2（跨租户写穿）、high 3（物理删）三条的修法都只收紧了一个入口。而且这不是假想形态——`tests/Pzd.IntegrationTests/PersistenceTests.cs` 里「软删除记录默认查询不可见且可显式绕过过滤」这条用例自己就写的是 `db.Updateable(user).ExecuteCommandAsync()`，说明下游一定会这么写。

改法（三选一，都要老何/老登定性）：
1. 在 AOP 里把 `UpdateByObject` 也拦下，只有 `PersistenceWriter` 内部的执行放行（需要内部标志位，实现要小心）；
2. 不拦，但把「禁止直连 `db.Updateable` / `db.Deleteable`」写成架构规则 + 13 号票的静态守卫（`src/` 下除 Infrastructure 外出现这两个调用即红），并在 06 票面把「唯一写入口」改成「唯一**被强制**的写入口 + 静态守卫」；
3. 只做 2 的一半：`Deleteable` 全形态拦（AOP 里判断 `OperationType == DeleteByObject` 对无实体形态加 SqlSugar 的 `ExecuteCommand` 前置拦截不现实，多半要靠静态守卫）。

我的倾向：**2 最省事且不漏**——AOP 拦条件删除在 SqlSugar 里没有干净钩子，静态守卫能把两条旁路一起管住，而且它是 13 号票的本行。

### high｜P3：回收站恢复现在无入口，用现有入口手搓必然破坏唯一索引

软删除后 `IsDeleted=1 / DeletedToken=Id / DeletedAt / DeletedBy=7`。要恢复，只能用 `UpdateAsync` 把 `IsDeleted` 改回 false——但 `WriteAsync` 里 `DeletedToken` 取的是 `ReadLong(entity, DeletedToken)`（即恢复时实体上残留的旧 Id），`DeletedAt/DeletedBy` 取实体原值。结果：

- `DeletedToken` 残留 = `2115993763838038016`（非 0）
- `DeletedBy` 残留 7、`DeletedAt` 残留 1 行
- 唯一索引 `(TenantId, UserName, DeletedToken)` 里这条是 `(1,'恢复',<Id>)`，新插的同名记录是 `(1,'恢复',0)`，**撞不上** → 同名重建成功，`活跃同名记录=2`

也就是说，`NOT NULL DEFAULT 0` 这套设计要防的「两条活跃同名记录」，恢复一次就复现了。架构 §5.3 承诺了回收站可恢复，06 现在没有 `RestoreAsync`，谁来实现 17/19 的回收站谁踩。

改法：补 `PersistenceWriter.RestoreAsync`，一次把 `IsDeleted=false / DeletedToken=0 / DeletedAt=null / DeletedBy=0` 四列写全（同样带版本与租户条件）；或者票面明确「本期不做恢复」，把 §5.3 的承诺改成「回收站只读，不支持恢复」——不能两处说法并存。

### high｜P1 + P2：插入路径完全没有租户闸，且不填 `TenantId`

更新侧现在「有租户列就必须有租户上下文，否则抛异常」，插入侧一个校验都没有，`PersistenceAudit.OnInsert` 也只处理 `Id/Version/时间/用户/DeletedToken`，**没有 `TenantId` 分支**：

- 无租户上下文插入 → 成功落库 `TenantId=0`，成为一条任何租户都改不到的孤儿行；后续在该租户上下文里 `UpdateAsync` 只会返回 `VersionConflict`（被 09 映射成 409 并发冲突），**错误分类是错的**——真实原因是租户不符，不是并发。
- 上下文是 1、实体填 2 → 成功，跨租户写入。

改法：`OnInsert` 里补 `TenantId` 分支——无上下文抛异常（与更新侧同口径），有上下文时覆盖为上下文值并警告「调用方填的值被忽略」；这是唯一能保证「插入即归属正确租户」的位置。

## 已排除的可能

- `db.Ado.ExecuteCommandAsync("DELETE FROM ...")` 原 SQL 当然绕过一切，但那是任何 ORM 都拦不住的已知边界，与 `.Where()` 形态性质不同，不计入。
- `SetColumns` 形态不写 `DeletedToken` 已被 06 票写成已知边界用例，不重复。
- P3 不是我的探针写错：软删除那一步我自己断言了 `restoreFailure=null`（恢复调用本身成功），残留是写入口的取值规则决定的。
