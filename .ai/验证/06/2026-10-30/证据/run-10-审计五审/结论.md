## 2. 本轮发现

### medium · `UpdateAsync` 认实体不认库：脱离实体能往已删除的记录上静默写入

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:169-190`（守卫只看实体上的 `IsDeleted`/`DeletedToken`）+ `:214`（`WHERE` 只有 `Id`/`Version`/`TenantId`，**没有 `IsDeleted = 0`**）；与之矛盾的表述在 `:83`（docstring「按版本条件更新一条**活跃**记录 …… 也不接受删除态或回收站里的实体」）与票面 `:242`（「且删除态实体直接拒绝」）
- **探针原文**：

  ```
  P8 脱离实体更新已删除记录：failure=null（成功，调用方以为改成了）；
     库里 IsDeleted=1 DeletedToken=2116007178610544640 UserName=已删-脱离-改名 Version=3；活跃记录数=0
  P2 用法二（改成 IsDeleted=false）：failure=null（成功）；
     库里 IsDeleted=1 DeletedToken=0 DeletedAt残留=1 UserName=存量删除-改名 Version=2
  ```

- **问题**：`P8` 里实体是典型「DTO 转回来更新」的形态——只带 `Id`、`Version`、业务字段，`IsDeleted` 默认 `false`、`DeletedToken` 默认 `0`。两道守卫（`IsDeleted` 为真、`DeletedToken` 非 0）都不触发，`WHERE` 又不带活跃条件，于是：业务字段被改、`Version` 加 1、**返回 `null` 表示成功**，而库里那行仍然是 `IsDeleted=1`，应用侧根本读不到它（软删除过滤器挡着）。
- **为什么错**：这是「防线认实体、不认库」——上一轮 P5a 那个「兜底只挡罕见形态」是同一类毛病的另一个面。加载回来的实体带着标记，所以被拦住；**从 HTTP 体回来的实体不带标记，反而穿过去**，而后者是 07/08 接 API 后最常见的形状。调用方拿到成功，随后按 `Id` 读却查不到，排查时会先怀疑缓存、再怀疑租户，最难怀疑到「写进了一条已删记录」。它还和票面自己写死的那句话直接冲突，属于「两处说法并存」。
- **修改建议**：
  1. `WriteKind.Update` 的 `WHERE` 追加 `AND <IsDeleted> = 0`（有 `DeletedToken` 的类型也可用 `AND <DeletedToken> = 0`），让**库**判定这行是否活跃。
  2. `affected == 0` 时别笼统返回 `VersionConflict`——先按 `Id + TenantId` 查一次：存在但已删除 → 抛 `InvalidOperationException`（消息点名「记录在回收站，要恢复请走 `RestoreAsync`」）；否则才返回 `VersionConflict`。否则 09 会把「已删」映射成 409 并发冲突，正是票面 `:258` 段已经为 `Version=0` 行记录过的那个坑。
  3. 补用例 `脱离实体更新已删除记录被拒绝`（形态照抄我 `P8`）。**这条现在完全没有用例守着**：我这轮 3 处变异没有一处能红到它，说明它不在测试网的覆盖里。

### low · 成功路径把「从未写进库的删除四列」套回调用方实体，内存与库分叉

- **文件与行**：`src/Pzd.Infrastructure/PersistenceWriter.cs:252`（`PersistenceAudit.ApplyUpdateStamp(entity, stamp)`）+ `src/Pzd.Infrastructure/PersistenceAudit.cs:215-216`
- **探针原文**：

  ```
  P4 更新后：failure=null；库里 DeletedAt为NULL=1 DeletedBy=0 IsDeleted=0 DeletedToken=0 Version=2
  P4 更新后：内存实体 DeletedAt=2020-01-02T03:04:05.0000000Z、DeletedBy=5、IsDeleted=False、DeletedToken=0、Version=2
  ```

- **问题**：这轮把删除四列从 `Update` 的 `SET` 里摘掉了（对），但成功之后 `ApplyUpdateStamp` 仍把 `stamp` 里的删除列写回实体，而 `stamp` 的删除列来自**实体自己**——也就是那批刚被判定「不写库」的值。结果库是 `NULL/0`，调用方手里的对象是 2020 年的 `DeletedAt` 与 `DeletedBy=5`。
- **为什么错**：票面 medium 3 的既定原则是「冲突时调用方实体保持原值」，本质要求是**内存实体要能代表库里的真实状态**。现在成功路径反而制造分叉：调用方若把实体直接序列化给前端，会看到一条活跃记录带着 2020 年的删除时间；再拿它做下一次 `UpdateAsync` 也仍然通过（`token=0`），问题被悄悄带下去。
- **修改建议**：`WriteKind.Update` 时 `ApplyUpdateStamp` 不碰删除四列；或者把四列按库的真实值（`IsDeleted=false`、`DeletedToken=0`、`DeletedAt=null`、`DeletedBy=0`）落到实体上。补断言到 `UpdateAsync不改动任何删除审计列`（现在只断言了库，没断言内存实体）。
