## high｜P5a：运行期兜底只挡「Version 漏填」，挡不住「Version 填对」——这是更常见的形态

新增的防御是 `if (Version <= 0) throw`（`PersistenceAudit.cs` 的 `UpdateByObject` 分支）。所以：

- 分离实体忘了设 `Version` → `Version=0` → 被拒（P5b 绿，雨哥的用例测的就是这个）；
- **调用方手里有正确 `Version`** → 放行，`db.Updateable(intruder)` 照样按 Id 更新：`TenantId` 1→2 整行搬走、`UserName` 被改、`CreatedBy` 抹成 0、`Version` 仍为 1。

而「加载→改→保存」的实体本来就带着正确版本号，这是最正常的用法。所以这条兜底挡住的恰恰是**罕见形态**，真正会发生的形态没挡住。

**P5c 的绿要反着读** ⚠️：旁路写完之后，甲租户拿旧快照走正规入口得到的是 `Persistence.Record.VersionConflict`——看似「并发保护还在」，实际原因是 `WHERE TenantId=1` 匹配不到已经被搬到租户 2 的那行了。真实后果是**甲彻底失去这条记录**，而且拿到的 409 会让人以为「有人先改了，我重载再试」，重载也永远读不到。这条绿不能当好消息，它是「记录被搬走」的旁证。

改法：运行期兜底没法区分「入口内」和「入口外」（同一套 AOP），`Version>0` 的形态在 AOP 层拦不住。结论是**13 票的静态守卫不可替代，也不能因为「运行期已兜底」而降级或删掉**；06 票「对外契约」那节应写明「运行期兜底只覆盖 Version 漏填一种形态，不是许可」。

## high｜P6：`UpdateAsync` 可以当恢复用，且会静默破坏唯一约束

`RestoreAsync` 加对了（P3 绿），但 `UpdateAsync` 传一个 `IsDeleted=false` 的回收站实体也照样跑完：`WriteKind.Update` 只把 `IsDeleted` 写回 false，`DeletedToken` 仍取实体上的残留值（`2115998007852929024`）、`DeletedAt/DeletedBy` 一并残留。结果唯一索引里这条是 `(1,'误用恢复',<Id>)`、新记录是 `(1,'误用恢复',0)`，撞不上 → 同名重建成功，`活跃同名记录=2`——正是 `NOT NULL DEFAULT 0` 这套设计要防的。

也就是：上一轮我把「恢复没入口」报成一条，现在入口有了，但**没有把错误用法关掉**，同一个坑还在。

改法：`WriteAsync` 里当 `kind == Update` 且实体 `IsDeleted` 由 true 变 false 时拒绝并提示走 `RestoreAsync`（用例名可叫「用UpdateAsync做恢复被拒绝」）；或在票面把「恢复只能走 RestoreAsync」写进契约，并用 P6 这条钉住。

## P4 仍红，且我同意这条运行期修不了

`db.Deleteable<ProbeUser>().Where(...)` 不带实体，AOP 的 `DeleteByObject` 不触发，`物理行数=0`。雨哥没假装拦住，这点我认——它只能靠 13 票静态守卫。**记录在此只为避免后面有人把「25 条全绿」读成「旁路全封」**。
