## 2. 三处实现复核：都对，而且是真的根治

1. **`MissKind` 去数字编码**（`PersistenceWriter.cs:352`、`:359-364`）：SQL 直接 `SELECT CASE … THEN 'NoRow' … THEN 'Recycled' ELSE 'Active' END`，`Enum.TryParse(ignoreCase: false)` 接，解析不出就 `throw` 带原文。「编码顺序与枚举声明不一致」这个失败模式**从代码里不存在了**，不是换了个恰好对上的写法——`(MissKind)code` 这种写法已经没有 code 可转。这是我七审 low 想要的结果，比「SQL 改 `THEN 1`/`ELSE 2`」高一个档。
2. **`RestoreAsync` 守卫整段删除**（`:140-146`）：能不能恢复交给 `WHERE … AND IsDeleted=1`（`:243-246`）。我五审 P8 指出的「DTO 形态穿过内存守卫」在恢复方向上被同一套思路收掉了——**活跃态由库判定，不由调用方实体自报**。这条与 06 五审的 Update 修法是一个口径，不是特例。
3. **第五种 `NotInTrash`**（`PersistenceErrors.cs:19-20`、`:65-73`，判定在 `PersistenceWriter.cs:286-292`）：`Kind=NotInTrash` / 409 / `Persistence.Record.NotInTrash` / 「这条记录不在回收站，无需恢复。」，与 `RecordInTrash` 的 code 分开，与 09 票 `698e4da` 一致。`:282` 先判 `Recycled && kind != Restore`、`:289` 再判 `Active && kind == Restore`、最后落 `VersionConflict`，三个分支互斥且顺序无关，可读。

我的原复核建议「`RestoreAsync` 只在实体自称已删除时返回业务态，其余抛异常」已被这次改造取代——手段比建议更彻底（把判断移到库里），旧建议作废，记在此处以免后续被引用。

## 4. 探针：删守卫后新开的输入面，我自己打了一遍


## 5. medium（挂 07，不阻塞本分支）：跨租户恢复没有任何用例守

**文件与位置**：`src/Pzd.Infrastructure/PersistenceWriter.cs:232-237`（`AND TenantId=@tenantId` 的拼装）
**现象**：M-E 只让 `Restore` 这一条路丢掉租户条件，`PersistenceTests` 36 条全绿。也就是说，把租户隔离从恢复路径上拿掉，整套用例一条都不会红。
**为什么错**：租户隔离在 PZD 的「必须先写失败测试」清单里（AGENTS.md 明确列入租户隔离与租户解析）。现在恢复路径的租户正确性只靠代码写对 + 探针（人肉），没有一条能红的断言；07 正是租户票，07 之后再有人动这里的 WHERE，谁都不会知道。注意这是**既有缺口**（改造前也没有），不是 6e 引入的，但删守卫扩大了可达面：改造前 DTO 形态会被守卫先拦掉，现在任何 DTO 都能走到这条 SQL。
**具体修改建议**：在 07 票的跨租户红用例里固定这一条——
```csharp
// 租户 1 的上下文恢复租户 2 的已删记录
var failure = await PersistenceWriter.RestoreAsync(db1, dtoWithTheirsId, OptionsFor(1), ct);
Assert.Equal(PersistenceFailureKind.NotFound, failure!.Kind);   // 不是 InTrash：不泄露别家存在性
// 别家那行原样：IsDeleted=1、DeletedToken≠0、TenantId=2、Version 不变
```
**归属**：交接 §4 已把「补跨租户红用例」派给 07。请张一一在 07 票面写死这一条（只写在交接里不够，07 的审计会按票面判）。
