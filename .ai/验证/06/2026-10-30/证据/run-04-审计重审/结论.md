## 四、本轮发现

### high 1｜票面「定型的软删除唯一索引方案」里的建表 SQL 缺 `DeletedAt`/`DeletedBy`

- 文件：`docs/work/cross-cutting/tickets/06-persistence-base.md` 定型方案节（`54dc57b` 第 52–75 行）
- 问题：这节是「供 17、19、20、23、32 号票复用」的权威 DDL，示例 `CREATE TABLE test_user` 只有 `DeletedToken`，**没有** `DeletedAt`、`DeletedBy`；而同一张票第 154、172 行明确写了「另按 §5.3 补 `DeletedAt DATETIME(6) NULL` 与 `DeletedBy BIGINT NOT NULL DEFAULT 0`」，代码与用例也都用到了。
- 为什么错：下游是照这节 SQL 块抄的，抄出来就是缺列的表。届时 `SoftDeleteAsync` 写 `DeletedAt/DeletedBy` 会直接报 `Unknown column`，而写用例的人会以为是 ORM 映射问题——错误指向完全错的方向。票面内部自相矛盾，比写错更难查。
- 修改建议：把这节的列定义补成与 `PersistenceTests.SchemaSql` 完全一致（含 `DeletedAt DATETIME(6) NULL`、`DeletedBy BIGINT NOT NULL DEFAULT 0`），并在「建表时必须一起带的约定」里把这两列列进去；顺手在票面注明「本节 SQL 与 `PersistenceTests.SchemaSql` 必须逐字同形，17 号票拿它做对照」。

### medium 1｜`UpdateAsync` 当软删除用会丢 `DeletedAt/DeletedBy`，且用例盖不到

- 文件：`src/Pzd.Infrastructure/PersistenceWriter.cs:96`（`ComputeUpdateStamp(..., markDeleted)`）与 `:157-168`（`ValueFor` 用 `deleting`）
- 问题：同一个方法里有两个布尔——`markDeleted`（`deleting || 实体 IsDeleted`）和 `deleting`。算审计值时传的是 `markDeleted`（所以 `DeletedToken` 会写对），拼 SET 的分支判断用的却是 `deleting`（所以 `DeletedAt/DeletedBy/IsDeleted` 三条分支对 `UpdateAsync` 全部不生效）。
- 为什么错：实测（探测 Q1，`UpdateAsync` + 实体 `IsDeleted=true`）：

  ```
  Q1 UpdateAsync(IsDeleted=true) failure=null DeletedToken=<=Id> DeletedBy=0 DeletedAt为NULL=True
  Q1 同名重建=成功
  ```

  `DeletedToken` 写对了、同名重建也放行，所以从行为上看像成功；但删除人和删除时间静默丢失。张一一的裁定是「`DeletedAt/DeletedBy` 必须有，回收站排序和『谁删的』靠它们」，这条路径等于把裁定绕过。变异 M7 证明现有 18 条用例完全不管这回事。
- 修改建议：统一成一个语义——`ValueFor` 也用 `markDeleted`；或者更干脆：`UpdateAsync` 检测到实体 `IsDeleted=true` 就抛异常，要求必须走 `SoftDeleteAsync`（与 `Deleteable` 的处理一致）。无论哪种，补一条用例：`UpdateAsync` 路径软删除要么写全四列、要么明确抛异常。

### high 3｜回收站恢复没有入口，恢复后同一业务键出现两条活跃记录

- 文件：`src/Pzd.Infrastructure/PersistenceWriter.cs`（无恢复入口）；`PersistenceSoftDelete.cs`（只有读侧过滤）
- 问题：架构 §5.3 承诺「回收站可恢复」，但本票只做了软删除，没做恢复。业务代码只能自己把 `IsDeleted` 置回 `false` 再 `UpdateAsync`。
- 为什么错：实测（探测 Q2）：

  ```
  Q2 删除后同名重建成功，活跃记录数=1
  Q2 恢复 failure=null；同名活跃记录数=2；恢复后 DeletedToken=<仍是 Id>
  ```

  恢复时 `DeletedToken` 仍保留 `Id`，于是唯一索引 `(TenantId, 业务键, DeletedToken)` 让两条同名记录都占着「不同的 token」——唯一约束对它失效。老记录恢复、新记录还在，两条活跃同名记录并存，违反本票最核心的那条 AC。
- 修改建议：加 `RestoreAsync`（或恢复也在 `WriteAsync` 里显式分支）：恢复时必须把 `DeletedToken` 归 0，并在同一次 UPDATE 里让唯一索引自己去撞——撞了就返回 `DuplicateKey`，表示「新记录已占用该业务键，不能恢复」。补一条用例钉住「恢复后同名活跃记录只能有一条」。

### high 4｜插入路径完全没有租户校验或注入

- 文件：`src/Pzd.Infrastructure/PersistenceAudit.cs`（`OnInsert` 只填审计与主键，不碰 `TenantId`）
- 问题：`TenantId` 由调用方在实体上自己填，AOP 不校验、不注入。
- 为什么错：实测（探测 Q3，上下文租户 = 1）：

  ```
  Q3 上下文租户=1，插入实体 TenantId=2 → 库里 TenantId=2
  Q3 实体未填租户 → 库里 TenantId=0
  ```

  写入口（UPDATE）现在守得很严，插入却是敞开的：错填就写进别家租户，漏填就是 `TenantId=0` 的幽灵记录，而架构 §6.1 是把 `TenantId` 当纵深防御用的。这类脏数据一旦产生，租户过滤会永久看不到它，只能靠人工捞。
- 修改建议：`OnInsert` 里若实体有 `TenantId` 列且 `options.CurrentTenantId()` 有值，就覆盖（或在不等时抛异常）；没有上下文时保持现状但至少写进票面。若老何认为插入归 07/08，请把这条写进 07 的验收，别让它悬空。

### high 2｜绕过 `PersistenceWriter` 直接用 ORM，租户/审计/并发三道闸全部失效

- 复现（`bypass-results.txt`，`BUILD_EXIT=0`、`Total: 3, Failed: 0`）：

  ```
  B1 Deleteable<T>().Where 未抛异常，影响行=1，物理行数=0
  B2 Updateable(entity) 影响行=1；TenantId=2 UserName=直改-被搬 CreatedBy=0 Version=0；基线 CreatedBy=7 Version=1
  ```

- 为什么错：
  1. `db.Deleteable<T>().Where(...)` 不带实体时，AOP 的 `DataExecuting`/`DeleteByObject` 根本不触发（它按实体逐列回调），所以上一轮加的物理删除拦截**只在「手边有实体」时有效**，条件删除一路放行，行直接没了。
  2. `db.Updateable(entity)` 按主键更新、不带版本与租户条件：实测把整行从 `TenantId=1` 搬到 `2`、`CreatedBy` 抹成 `0`。
  3. **比李总报的更严重**：`Version` 不是「不自增」，而是被实体上的默认值直接写成 **0**（基线 1 → 0）。之后所有走 `PersistenceWriter` 的更新都拿 0 去比，永远对不上，等价于该行永久锁死；同时 `Version=0` 也骗过了任何按版本判活的逻辑。
- 为什么这条评 high 而不是 medium：这不是「少了个校验」，而是**本票宣称的三条保障（租户谓词、创建审计、乐观并发）有一条完全可绕的路**，而且现有用例自己就在示范这条路（`软删除记录默认查询不可见且可显式绕过过滤` 用的是 `db.Updateable(user)`）。下游 17/19/20/23/32 会照着用例学。
- 修改建议（与张一一在 13 号票的裁定 `cc10f6c` 一致，我认可并补充三层）：
  1. **静态守卫（主）**：`src/` 下除 `Pzd.Infrastructure/**` 外出现 `db.Updateable(` / `db.Deleteable(` / `db.Insertable(` 一律判红；Infrastructure 内部只允许 `PersistenceWriter`，物理删除设显式白名单（08 的 outbox 清理要豁免，列名单不列通配符）。
  2. **改写示范性用例**：`软删除记录默认查询不可见且可显式绕过过滤`、`软删除后能用同一业务键重建` 两条现在用 `db.Updateable(user)` 演示错误写法，应改成走 `PersistenceWriter.SoftDeleteAsync`，否则守卫上线后它们自己就得开豁免。
  3. **票面写死**：06 的「对外契约」节补一句「业务代码只允许 `Queryable` 读、`PersistenceWriter` 写；任何 `Updateable`/`Deleteable`/`Insertable` 都算违约」。
