# user-management 规格：标杆模块（M5）

> 基线：2026-10-29（v1）　作者：老何
> 需求依据：[architecture.md](../../architecture.md) §3.1、§4 Identity、§7.2、§9.3、§14.3、§16.1、§16.2
> 拆分依据：[consensus.md](../pzd-v1/consensus.md) M5（M5.1–M5.4）
> 本里程碑的产物是**后续所有业务模块的模板**，不是一次性的用户管理页

## 1. 问题

底座、租户、认证、外壳都有了，但还没有一条真正的业务链路被走通。没有标杆模块，后面接业务模块时每个人会自己发明命名、分层、错误码、权限码和页面结构，约定会分裂。

## 2. 方案

用 Identity 用户管理做一条完整全链路：聚合 + 仓储 + Command/Query + 端点 + 权限码 + 数据范围 + 前端表格与表单，把过程中形成的约定写进 `CLAUDE.md`，并用 Playwright E2E 把「登录 → 权限 → 增删改查」固化成回归基线。出口是「E2E 覆盖增删改查与权限」。

## 3. 用户故事

1. 作为租户管理员，我想看到用户列表并分页、排序、按关键字筛选，以便找到要处理的人。
2. 作为租户管理员，我想新建用户并设置用户名、姓名、手机号、邮箱、角色、部门，以便入职即开通账号。
3. 作为租户管理员，我想编辑用户资料和角色，以便调岗或改权限。
4. 作为租户管理员，我想重置用户密码，以便对方忘记密码时不用重建账号。
5. 作为租户管理员，我想停用而不是删除用户，以便历史记录仍可追溯。
6. 作为租户管理员，我想删除用户后能在回收站语义下恢复（本里程碑只做软删除与不可见，恢复界面期外），以便误删可挽回。
7. 作为租户管理员，我想新建用户名重复时看到字段级错误，以便知道换个名字。
8. 作为租户管理员，我想两个人同时改同一用户时被提示数据已被修改，以便不静默覆盖别人的改动。
9. 作为无用户管理权限的账号，我不想看到用户管理菜单，以便界面干净。
10. 作为实现 Bot，我想照着这个模块抄结构就能接新业务模块，以便不用每次重新讨论分层。
11. 作为实现 Bot，我想错误码、权限码、DTO 命名都有既定格式，以便不同人写出来是一致的。
12. 作为审计 Bot，我想有一条 E2E 命令能跑通增删改查，以便判断改动是否弄坏了标杆链路。

## 4. 实现决策

- 后端沿用 `Pzd.Identity` 模块的五层结构（Domain / Application / Infrastructure / Endpoints / `IdentityModule.cs`），新增用户管理相关的聚合与端点，不新建模块。
- 用户聚合守护不变量：用户名唯一（`(TenantId, UserName)` 唯一索引，含软删除考虑）、必填字段、角色分配走聚合方法 `AssignRoles(...)`、停用与删除走领域方法。
- 读侧走 CQRS-lite：列表查询用 SqlSugar 直接投影 DTO，不经聚合加载。
- 权限码：`system:user:query|create|update|delete|reset-password`（按 §7.2 格式，模块前缀沿用 `system`，因为这些是系统管理功能）。权限码在 19 号种子中已存在，本票只做端点挂载与前端 `<Can>` 使用。
- 数据范围：列表查询按当前用户角色的数据范围追加条件；「仅本人」只能看到自己。
- 错误码：`Identity.User.NameDuplicated`、`Identity.User.NotFound`、`Identity.User.Disabled` 等，文案集中在模块 `Errors` 类。
- **审计日志边界（已决定）**：本里程碑只写 Serilog 技术日志，并在端点处保留审计扩展点（一个可替换的 `IAuditWriter` 接口位）。业务审计日志表与界面属原 M6.6，期外，**不作为本票依赖**（据此去掉 consensus 里 M5.1 对 M6.5 通知的依赖：标杆模块不发通知）。
- 前端：TanStack Table + shadcn data-table，分页/排序/筛选放 URL；表单 react-hook-form + zod；删除与停用需二次确认。
- `CLAUDE.md` 在 34 号票定型：命名、分层、错误码、权限码、前端页面结构、测试放置。**M6 及以后大面积页面开发必须等它定型**。

## 5. 测试决策

- **强制测试先行**：权限码与数据范围、状态流转（停用/启用）、幂等与并发冲突。先写失败测试并确认失败原因正确。
- 聚合不变量用单元测试（不连数据库）：重复用户名返回 `Result.Failure`、停用用户不能登录。
- 端点行为用集成测试（真库）：403/422/409 三类代表性反例必须各有一条。
- E2E（Playwright）覆盖：登录 → 看到菜单 → 新建用户 → 列表可见 → 编辑 → 删除 → 列表消失；以及无权限账号看不到菜单与按钮。
- 不测实现细节（如仓储调用次数、DTO 内部字段顺序）。

## 6. 非目标

- 不做业务审计日志表与审计页面（原 M6.6，期外）。
- 不做通知（原 M6.5，期外）：标杆模块不发送站内信或邮件。
- 不做回收站恢复界面（原 M6.8，期外）：只做软删除后的不可见。
- 不做完整组织架构维护（部门/岗位维护界面期外），只依赖 20 号票的最小骨架。
- 不做用户导入导出、批量操作、密码策略配置界面、在线用户与强制下线。
- 不做平台超管的跨租户用户管理。

## 7. 验收标准

- **AC-01** 有 `system:user:query` 的账号能分页查询用户列表，筛选与排序改变后 URL 同步变化。
- **AC-02** 新建用户成功返回 201 且列表可见；用户名重复返回 422 且 `errors.userName` 有值，库里不产生第二条记录。
- **AC-03** 编辑用户角色后，该用户重新请求 `/api/me` 得到新权限码（缓存已失效）。
- **AC-04** 停用用户后该用户登录被拒绝（422 或 403，`code` 明确）；重新启用后可登录。
- **AC-05** 删除用户后列表不再显示，且原唯一索引不阻止用同名新建（软删除与唯一索引的约定成立）。
- **AC-06** 两个会话同时编辑同一用户，后提交者收到 409。
- **AC-07** 无 `system:user:delete` 的账号看不到删除按钮，且直接调用删除端点返回 403。
- **AC-08** 数据范围为「仅本人」的账号查询列表只返回自己。
- **AC-09** `CLAUDE.md` 存在并写清命名、分层、错误码、权限码、前端页面结构与测试放置，且与实际代码一致（抽查三处）。
- **AC-10** `pnpm e2e` 一条命令跑通「登录 → 菜单 → 增删改查 → 权限」用例，退出码 0。

## 8. 假设与待决

- **A1** 20 号票（最小组织骨架）先完成，否则用户表单的部门字段降级为纯文本输入，并在遗留里写明。
- **A2** 密码策略的具体强度要求沿用 23 号票的认证实现，本票不重复定义。
- **A3** E2E 需要的测试租户与账号由 35 号票的初始化脚本准备，若脚本尚未就绪，用 21 号开通流程手工准备并在票里记录账号来源（不写密码）。
