# platform-identity 规格：Platform + Identity（M3）

> 基线：2026-10-29（v1）　作者：老何
> 需求依据：[architecture.md](../../architecture.md) §4、§6.1、§6.3、§6.4、§7.1、§7.2、§7.3、§15.4
> 拆分依据：[consensus.md](../pzd-v1/consensus.md) M3（M3.1–M3.7）
> 已决口径：菜单与权限的最小种子前置到本里程碑（原待决 1，见 §4 决策 D1）

## 1. 问题

平台侧现在没有任何东西：没有 master 库表，没有租户，没人能登录，登录后也拿不到自己能看什么。前端外壳（M4）和标杆模块（M5）都等着「新租户可登录、能拿到权限码与菜单」这个出口。

## 2. 方案

建 master 库结构与迁移、租户与套餐模型、租户开通流程（分步可重试）、租户库迁移与运行时版本校验、Cookie 认证、基于权限码的授权模型，以及 `/api/me`。出口是「新租户可登录」。

## 3. 用户故事

1. 作为平台超管，我想创建租户并指定套餐，以便给客户开通一套独立库。
2. 作为平台超管，我想看到开通任务分步执行结果，以便某步失败了能只重试那一步。
3. 作为平台超管，我想看到每个租户的库版本，以便判断谁还没迁移。
4. 作为租户管理员，我想用账号密码登录并保持会话，以便不用每次刷新都重新登。
5. 作为租户管理员，我想输错密码多次后被锁定，并看到图形验证码，以便账号不被暴力破解。
6. 作为租户管理员，我想登录后立刻拿到自己的权限码和菜单树，以便界面只显示我有权使用的东西。
7. 作为租户管理员，我想角色权限变更后立刻生效，以便不用重新登录。
8. 作为租户管理员，我想在升级期间看到「系统升级中」而不是一堆报错，以便知道不是自己操作错了。
9. 作为平台超管，我想租户停用或到期后该租户所有人立刻无法访问，以便合同到期能真正切断。
10. 作为开发 Bot，我想套餐决定这个租户最多能分配哪些权限码，以便不同版本卖不同功能。
11. 作为运维，我想发布顺序固定为「先迁移、后部署」，以便旧代码在新表结构上仍然能跑。
12. 作为实现 Bot，我想数据范围留出五档的位置，以便后续组织架构接入时不用改授权模型。

## 4. 实现决策

**D1 菜单与权限种子提前（回答 consensus §4 待决 1）**
- `menus` / `permissions` 表结构在 17 号票建；**最小可用种子**（登录后必须存在的菜单项与 V1 全部权限码）在 19 号票落地，随 master 库迁移一起初始化。
- 完整维护界面（增删改菜单、权限码管理）仍属原 M6.2，**期外**，不在 V1 范围内排票。
- 理由：`/api/me`（M3.7）与用户管理页（M5.2）都依赖菜单项存在，若等 M6 就会让 M3/M5 的验收无法自洽。

**D2 租户库迁移执行器未定（consensus §4 待决 2）**
- 规格只写约束，不选型：版本化 SQL 放 `db/tenant/`、执行记录进各库 `schema_versions`、逐租户执行、支持灰度、单租户失败只标记该租户、脚本必须兼容旧代码（expand-contract）、发布顺序「先迁移后部署」。
- 选型由维护者/实现者在 22 号票的实施说明里写下结论，不得在本规格里预埋。

**库与模型**
- master 库：`tenants`、`tenant_packages`、`menus`、`permissions`、`platform_users`、`qrtz_*`、`schema_versions`。
- 租户库：`users`、`roles`、`user_roles`、`role_permissions`、`depts`、`schema_versions`、`outbox` 等；**保留 `TenantId` 列与 QueryFilter**（纵深防御）。
- 租户状态机：`待开通 → 开通中 → 可用 → 停用 / 到期`；开通失败记在租户上，不改其他租户状态。
- 套餐 → 权限码上限：租户能分配的权限码集合 = 套餐允许集合。默认套餐 `BASIC` 由迁移脚本初始化，含 V1 全部权限码（回答 consensus §4 待决 6）。
- 连接串用 Data Protection 加密存 master，仅内存解密。

**认证（§7.1）**
- ASP.NET Core Identity + 同源 Cookie（`HttpOnly`、`Secure`、`SameSite=Lax`）；会话存 Redis；登录、登出、图形验证码、失败锁定、密码强度；开发期 Vite 代理保持同源。
- 认证方案按 scheme 组织，为将来 PDA Bearer 预留 Policy Scheme，业务代码不变。

**授权（§7.2）**
- 权限码格式 `{模块}:{资源}:{动作}`；用户—角色—权限码多对多；角色带数据范围五档（全部 / 本部门 / 本部门及下级 / 仅本人 / 自定义）。
- 后端自定义 `IAuthorizationPolicyProvider`，端点 `.RequirePermission("...")`；权限缓存 key 含租户与用户，变更经领域事件失效。
- 数据范围基于 Organization 的数据追加 QueryFilter 条件。**V1 的部门数据来自提前切片的最小组织骨架（20 号票）**，不含完整组织维护界面。

**`/api/me`**
- 返回用户信息、权限码列表、菜单树；菜单按权限码过滤；未登录 401。

## 5. 测试决策

- **强制测试先行**：租户隔离与租户解析、权限码与数据范围、租户状态流转。先写失败测试并确认失败原因正确，再实现。
- 授权测试只断言 HTTP 可观察结果（403/200、返回的菜单项集合），不断言内部缓存结构。
- 租户开通用集成测试覆盖「某一步失败 → 该租户标记失败、其他租户继续、重试只补失败步」。
- 登录安全的正反例：连续失败达阈值后即使密码正确也拒绝（正例）；验证码错误时不消耗失败计数（反例）。
- 停用/到期租户：持有有效 Cookie 也必须 403（正例，证明每请求校验）；重新启用后可再次访问（反例对照）。

## 6. 非目标

- 不做完整菜单/权限维护界面、字典、参数、编号规则、通知、回收站（原 M6，期外）。
- 不做完整组织架构维护（部门增删改、岗位、主管层级维护），只做最小骨架（20 号票）。
- 不做部门主管审批解析（M7，期外）。
- 不做平台超管跨租户切换界面（§6.3 的管理动作，期外）；后端只保留显式切换并写审计的接口位。
- 不做备份恢复。

## 7. 验收标准

- **AC-01** master 库迁移可从空库执行到最新版本，`schema_versions` 有记录；重复执行幂等。
- **AC-02** 创建租户后 `tenants` 记录含编码、状态、套餐、到期时间、加密连接串、库版本；连接串在库中是密文。
- **AC-03** 租户开通按步执行，某步失败时该租户状态为「开通中 + 失败原因」，其他租户不受影响，重试只补失败步并最终到「可用」。
- **AC-04** 租户库迁移脚本能对指定租户（或灰度批次）执行，单租户失败只标记该租户；脚本不破坏旧代码所需结构。
- **AC-05** 运行时租户库版本低于代码要求时，该租户请求返回 503 且 `code = Tenant.Upgrading`。
- **AC-06** 新租户管理员可登录（200 + Set-Cookie 含 HttpOnly/Secure/SameSite=Lax），登出后原 Cookie 失效。
- **AC-07** 连续密码错误达阈值后账号锁定；验证码错误返回 400 且不增加失败计数。
- **AC-08** 未登录访问 `/api/me` 返回 401；登录后返回权限码列表与按权限过滤后的菜单树。
- **AC-09** 无某权限码的账号访问对应端点返回 403；授予该权限码后无需重新登录即可访问（缓存已失效）。
- **AC-10** 数据范围「仅本人」的用户查询列表只返回本人数据；「全部」的用户返回本租户全部数据；两者都看不到其他租户数据。
- **AC-11** 租户被停用或到期后，持有效 Cookie 的请求返回 403 `Tenant.Disabled` / `Tenant.Expired`；重新启用后恢复。
- **AC-12** 分配超出套餐上限的权限码被拒绝（422，`code` 明确）。

## 8. 假设与待决

- **A1** 20 号票（最小组织骨架）先于 24 号票完成，否则数据范围五档只能验证「全部 / 仅本人」两档，其余两档顺延并在这张票的遗留里写明。
- **A2** 迁移执行器选型未定 → 22 号票实施条件为「待满足」。
- **A3** 平台超管的创建方式（种子账号 vs 手工 SQL）未定，17 号票按「迁移脚本插入一个超管种子，密码在首次启动时强制修改」实现；维护者若要别的做法需在票里批注。
